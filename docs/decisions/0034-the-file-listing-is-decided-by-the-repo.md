# The `?` file listing is decided by the repo, not by a hardcoded skip-list — one app-level VCS-directory prune excepted

`collect_files` walked with `walkdir` and skipped directories through `PICKER_SKIP_DIRS`, which held exactly one entry — `"node_modules"`. That is a hand-rolled **one-entry approximation of `.gitignore`**, and this repo's `.gitignore` also names `node_modules` (line 10, one line ABOVE `dist`), `dist`, `src-tauri/target`, `*.local` and `.research/`. Measured here as a real Space **at design time**: **12,625 files reachable, 11,880 of them build output, 424 of them git-tracked** — so with `MAX_PICKER_ENTRIES = 5_000` and a deterministic sorted walk the budget is consumed inside `src-tauri/target/` and a real file in any directory sorting after it is silently dropped from the picker. **Those three numbers are a dated measurement taken while this ADR was drafted (2026-10-09), not a live specification, and they do not reproduce today:** re-measured while correcting this document, `git ls-files` reads 426 and `src-tauri/target` alone holds over 30,000 files, so the pre-change reachable set is now far larger than 12,625. What survives is the ratio, which is the actual argument — build output swamps the cap on any repo that has been built in. Do not quote 12,625 / 11,880 / 424 as the current state of this repo. We decided: replace `walkdir` with **`ignore`** (the walker `ripgrep` itself is built on, pure Rust, statically linked) and let **the repository's own ignore rules decide visibility** — with TWO things kept: `hidden(false)`, so the deliberate dot-FILE rule survives exactly as ADR 0033 left it, and a directory-level prune which is the ONLY name rule the app applies.

**AMENDED 2026-10-09 at `2e63869`, before this ADR merged.** That prune is the **VCS metadata directories** — `.git`, `.hg`, `.svn` — where this ADR originally shipped ADR 0033's blanket dot-directory rule. The shape of the decision is untouched (the repo decides what its listing shows, and the app keeps exactly one rule that no ignore file can ever speak for); what changed is that the exception is now the size of the thing it actually has to be. See "The one app rule the repo cannot override" below.

**Supersedes ADR 0033 PARTIALLY — two clauses, and be exact about which two.** **(1) Its listing-visibility clause — both halves of that sentence, though they fell at different times.** 0033 describes the walk as "dot-dirs and `node_modules` skipped". The `node_modules` half went first, here: the skip-list is deleted and the repo's ignore rules decide. **The dot-directory half went at `2e63869`**, on this branch and before this ADR merged: `is_skipped_dir` no longer prunes every directory whose name begins with `.`, it prunes the three VCS metadata directories — at any depth below the Space root, unconditionally, whatever the repository declares — and lists every other dot-directory the repo has not excluded. So that sentence in 0033 is now false IN FULL rather than half-false, and what survives of its shape is ONE app-level name rule where it described two. **(2) 0033's async-safety clause, which claims an empty `filtered` means NO picker renders.** That is no longer true of the code: `ComposerMentions` renders on `open && (filtered.length > 0 || note)`, so a `note` ALONE renders the box over an EMPTY row list (the case it exists for — "the listing is capped" is what explains an empty picker). That widening shipped in the same squash-merge that brought 0033 in (`ef9a34b`), and this ADR, written later, did not cover it. The safety property 0033 was protecting is intact and unchanged: every keyboard branch is gated on `filtered.length > 0` (`ComposerRow.tsx`), so a note-only picker has no row to highlight and Enter still falls through to send. The accurate rule to carry forward is: **empty rows ⇒ no selectable rows and Enter still sends; a note may still render the box.** Any future prefix must preserve THAT, not the stronger sentence.

Everything else in 0033 STANDS untouched: `?` inserts a PATH and not contents, no `MentionKind`/block/chip, `expandMentions` / `splitMentionBlocks` / `mergeDedupeKey` never see it, Space-only scope, verbatim case preservation, the trigger grammar requiring ≥1 path char, and the reasoning that the agent's own Boundary-gated `read` stays the single enforcement point.

**Three axes decide the listing, and they are independent — do not collapse them.** **Scope** = where the walk roots (**Space** only, unchanged by this ADR). **Visibility** = which of those files may appear (the repo's ignore rules PLUS one app-level prune no repo can override — the VCS metadata directories, amended at `2e63869` from the blanket dot-directory rule this ADR first shipped; nothing else is the app's to hide). **Reach** = where those rules are read from (repo directories, never the user's machine-wide git config — with the ONE accepted leak recorded under Consequences below). A reader who takes "the picker is Space-only" as answering all three re-introduces the bug above. See the **Listing** entry in `CONTEXT.md`.

**The one app rule the repo cannot override: the VCS metadata directories are pruned.** "The repo decides" is the change this ADR made; it is still not the whole rule, and saying it flat is the inaccuracy this section exists to kill — but the exception is now one narrow name rule instead of a whole naming convention. `is_skipped_dir` (`src-tauri/src/commands/files.rs`) prunes a DIRECTORY whose name is in `PRUNED_VCS_DIRS` — `.git`, `.hg`, `.svn` — at any depth > 0, unconditionally and independently of what any ignore file says, and `filter_entry` prunes its whole subtree, so the walker never descends into it. **Everything else is the repo's call, dot-named or not:** `.github/`, `.vscode/`, `.claude/` and a `.venv` nobody ignored are walked and listed unless an ignore file excludes them, which is what `rg --hidden` does. Measured here 2026-10-09, this repo's listing is 426 entries with `truncated = false` and `rg --hidden --files --glob '!.git/'` prints 426 — the same set (a dated probe, not a live spec).

**Why the app keeps even this one:** `.gitignore` cannot exclude `.git/`, because `git` does not ignore its own metadata — so this is the ONE thing no repository can be asked to declare, and the only name rule the app may hold without recreating the defect this ADR's title rejects. It is also the only thing that CAN keep `.git/` out of the walk: `hidden(false)` — kept precisely so `?.env` completes — switches OFF the walker's own hidden filter, and the `ignore` crate does not exclude `.git` from a walk by itself (it only READS from it, for `.git/info/exclude`). Descending into VCS internals is never a wanted completion — unpruned, the picker offers thousands of `.git/objects/…` paths and spends the entry cap on them. `.hg` (Mercurial) and `.svn` (Subversion, which keeps one per working directory, hence the any-depth rule rather than a root-only one) are the same machine state for the other two VCSs whose checkouts get opened as a **Space**. The prune is DIRECTORIES ONLY, so a submodule's gitfile — a FILE named `.git` — is still offered, which is pinned as a decision (`collect_files_lists_a_file_named_git_because_the_prune_is_directories_only`) rather than left as an accident of `filter_entry`.

**What it costs, accepted.** (1) An app-side name list exists again — `PRUNED_VCS_DIRS` — which is the shape of thing this ADR argues against. It is held to the three names no ignore file can speak for precisely so it cannot slide back into a build-output blacklist: `node_modules`, `dist`, `target` and `.venv` are NOT in it and their absence is pinned (`collect_files_lists_node_modules_when_the_repo_declares_it_source`, and `PRUNED_VCS_DIRS`' own comment). (2) A heavy dot-directory nobody ignored is now walked, and can consume the entry cap and crowd real source out of the listing — pinned as a decision rather than left as a surprise by `collect_files_lets_a_non_ignored_dot_directory_eat_the_cap`, because `.` sorts before every letter. The remedy is the repo's own (a `.gitignore` or `.ignore` naming `.venv/`), never a name list up here.

**The question this section used to leave open, now decided.** This section formerly ended "whether the prune should narrow to VCS directories is an open design question, UNDECIDED, recorded as item 5 of Out of scope in `docs/roadmap/file-completion-listing.md`", and pre-empted it with "NO document may state that visibility is entirely the repo's decision". **The question landed at `2e63869` and the answer was yes**, so that forward-reference is closed here and the roadmap item is retired to a completed task (Task 6) rather than left dangling. What it bought, measured on this repo the same day (`git ls-files` = 426): the listing went 423 → 426 entries and now equals that count exactly, `truncated = false`, with NO `.git/…` path in it, and five entries carrying a dot-named component — `.github/workflows/ci.yml`, `.github/workflows/release.yml`, `.vscode/extensions.json` (the three this section used to cite as permanently unlistable), plus the two dot-named FILES that were always listable, `.gitignore` and `src-tauri/.gitignore`. A Space's **Skill** discovery roots (`<level>/.agents/skills`, `<level>/.pi/skills`) are listable for the same reason. Those numbers are a dated probe, not a live specification.

**And the Listing is still NOT by definition the tracked set.** That equality is a property of this tree at that moment, not a rule: untracked-but-not-ignored files are listed too (there happened to be none when the two counts matched), and any tracked file an ignore file excludes is not. The definition is the repo's non-ignored files minus the VCS metadata directories — nothing else is subtracted.

**Considered Options**

- **Extend `PICKER_SKIP_DIRS` with `dist` and `target`**: rejected — fixes THIS repo in one line but stays a hardcoded guess at someone else's build layout; a user's `.venv/`, `build/`, `.next/` or `vendor/` still floods their cap. The defect is the hardcoded list itself, not its contents.
- **Adopt `ignore` with `git_ignore(false)`** (use the crate only for its sorted walk and pruning API): rejected — keeps today's visibility exactly and gains nothing; the build-output flood stays (the 11,880 above is the design-time count, and it is an undercount today — the order of magnitude is the argument).
- **Full ripgrep parity, `git_global(true)`**: rejected — the listing would then depend on `~/.gitconfig`'s `core.excludesFile` and `$XDG_CONFIG_HOME/git/ignore`, so the same Space lists differently on two machines and a file can vanish for a cause invisible anywhere in the project. That is the *same defect class* as `exec_find`'s fd-vs-fallback divergence (both make behaviour a function of the user's environment), and we refused it here rather than fix it there.
- **`require_git(false)`** (honour `.gitignore` in non-git folders too): rejected — per the crate docs it also reads `.gitignore` from parent directories ABOVE the git root, which re-imports the machine/home reach excluded above through a different door (a stray `~/.gitignore` would decide every Space under it).
- **A custom `.archimedesignore` filename**: rejected — YAGNI. `.ignore` is the existing cross-tool convention, is read by default, and outranks `.gitignore` in the crate's precedence order, so it is already the override knob.
- **Keep the blanket dot-directory prune** (this ADR's original position): rejected at `2e63869` — it made the app override the repo on the exact axis this ADR assigns to the repo, and it did so at a cost measurable in this very repository (`git ls-files` tracks `.github/workflows/ci.yml`, `.github/workflows/release.yml` and `.vscode/extensions.json`, all non-ignored, none completable). Keeping `.git/` out never needed the blanket rule — it needed the three names in `PRUNED_VCS_DIRS`.

**Consequences**

- **`PICKER_SKIP_DIRS` is deleted, including its `node_modules` entry.** The intended consequence: a repo that *commits* `node_modules` and declares nothing against it now lists into it — which is what you want while debugging a dependency, and is the honest meaning of "the repo decides" (bounded only by the VCS-directory rule above, which pointedly does NOT name `node_modules`). **That example is HYPOTHETICAL and is NOT reproducible in this repo:** `node_modules` is line 10 of our own `.gitignore`, so `?` never walks into it HERE — the ignore rule prunes it exactly as the deleted constant used to, and what changed is WHO decides, not what is pruned here. The behaviour is demonstrated by `collect_files_lists_node_modules_when_the_repo_declares_it_source`, whose fixture declares NOTHING (no `.git`, no `.ignore`) rather than by any Space a reader can open.
- **The override is a `.ignore` file, not a new app setting.** It needs no git. One caveat must ship in the user-facing docs: git's rule that a file under an excluded **directory** cannot be re-included means `!dist/app.js` resurrects nothing once `dist/` itself is excluded — the negation has to target the pattern that excluded the *file*.
- **A non-git Space lists everything**, because git rules are repo-scoped (`require_git` stays at its default). The documented remedy is a `.ignore` file, which is not git-scoped.
- **Dot-FILES stay listable** (`hidden(false)`), so `?.env` still completes — but a gitignored dot-file (`*.local` here) does not, because the repo declared it not source. This keeps ADR 0033's deliberate choice while making the exception principled.
- **The bug class was CI-invisible and will be again unless the test says otherwise.** The tests pass on tiny temp fixtures with no build output, and CI has none either, so nothing could see a cap eaten by `target/`. The regression test the Consequences draft asked for — "a fixture large enough to overrun the cap" — ships as `collect_files_build_output_cannot_eat_the_cap_and_hide_source`: a fake `build/` of FOUR files under a `cap = 3`, plus one source file in a directory sorting after it (`src/app.rs`). **Small cap, tiny fixture, same assertion**: the cap only has to be smaller than the build tree for the bug to be visible, so four files under a cap of 3 make exactly the point a fixture of thousands would, at none of the cost — no test may depend on this repo having been built, and a test that needs thousands of files to bite is a test nobody writes. It is pinned to `.gitignore` + a `.git` DIRECTORY and deliberately NOT to an `.ignore` file, so it reddens if the git rules are ever switched back off.
- **`ignore` is a library, not a tool the user installs** — nothing external is invoked by the `?` path on any platform, and that was already true. (The availability concern that prompted this investigation belongs to the agent's `fd` / `rg` shell-outs in `agent/tools/exec.rs`, which this decision does not touch.)
- **One reach leak is accepted, deliberately: an ancestor `.ignore` above the repo root DOES apply.** `parents(true)` — needed so a Space opened at a monorepo PACKAGE inherits the repo root's rules — reads `.ignore` files from ancestor directories, and `.ignore` is NOT gated by the `.git` barrier that scopes the git matchers. So an `~/.ignore` above a repo affects every Space under `$HOME`, while a `~/.gitignore` there does not (that one stays refused: `git_global(false)`, `require_git` at its default). This is `ripgrep`'s own behaviour, and the price of package-level Spaces; nothing here or in `CONTEXT.md` may state that reach is bounded to the repo without carrying this exception. The code comment on `collect_files` is the authoritative record.

**Pinned by test.** `.git` is pruned by `filter_entry`, while `git_exclude` must read `<repo>/.git/info/exclude` — so whether the two are compatible was a belief about `ignore`'s internals when this ADR was drafted, and it said a test would decide it rather than this document claiming it. A test decided it, and the belief held: `collect_files_honours_git_info_exclude_while_never_listing_git_itself` (`src-tauri/src/commands/files.rs`) passes — a file named in `.git/info/exclude` is absent from the listing while no `.git/…` path is ever listed. The mechanism is now recorded rather than assumed: the crate builds a directory's matchers when the walker PUSHES that directory (reading `<dir>/.git/info/exclude`, resolving worktree `commondir`), which is INDEPENDENT of `filter_entry` — that closure only suppresses yielded entries and descent, so pruning `.git` from the results cannot unbuild the matcher built from it. Fixture note: a plain `.git` DIRECTORY, not a worktree-style `.git` file — the crate parses `gitdir:` + `commondir` for the latter, but a malformed one silently disables `exclude`, and the directory is the deterministic choice.

*Extended by ADR 0035 (2026-10-09).* The `?` picker gained a second and genuinely different mechanism — **Directory completion**, which lists ONE directory for a token beginning `/`, `~/` or a Windows drive root (`C:/`) — so out-of-Space paths are reachable without a **Listing** of them. Nothing in this ADR's three axes is corrected by it, and **scope** stays "the **Space** only", because Directory completion is not a Listing: it shares this ADR's visibility engine, its cap, and the two app rules above. Two consequences carry forward, and the second one corrects a reading this note originally invited.

1. **Reach.** `parents(true)` means the accepted ancestor reach applies to an ARBITRARY directory the user completes into, not only to the Space.
2. **Reach, in full, because "ancestor `.ignore`" understated it.** Out here the rules are read from the queried directory AND its ancestors, so an ancestor repository's `.gitignore` and its `.git/info/exclude` decide the peek too, and the nearest ancestor holding a `.git` is the git ROOT of the read. Line 34 refuses `require_git(false)` because it "would read `.gitignore` from parent directories ABOVE the git root", and that refusal stands: the barrier is the git root, and nothing above it reaches in. But a **Space** is normally opened AT a repository root, while a completed directory is usually deep in a tree, so line 46's sentence "a `~/.gitignore` there does not [apply]" is TRUE ABOVE THE GIT ROOT and FALSE when `$HOME` is itself a repository, which the dotfiles layout makes common. On that layout `~/.gitignore` and `~/.git/info/exclude` decide every `?~/…` listing, silently, with `truncated` false. Pinned by `completion_dir_inherits_an_ancestor_repositorys_gitignore` and `completion_dir_reads_the_nearest_ancestor_repositorys_exclude_and_stops_above_it`. Read lines 34 and 46 together with this paragraph, or the pair reads as a guarantee that no home-level git file can ever affect completion, which is not what shipped.


*Extended by the post-review pass (2026-10-10).* One heading above needs a word changed in the reader's head, because it now says "the one app rule the repo cannot override" and there are TWO. `a540e23` added `name_is_completable`: a NAME carrying `?` or a newline is refused by both walks, and a DIRECTORY whose name carries one is not descended into either. Read it against this ADR's title, because it is not a third convention. It asks whether a name can survive a round trip through the composer's token grammar, not whether the user may see the file, so it consults no project policy, no name list, and no maintainer taste: `?` and newline are the only two bytes the grammar cannot carry, anywhere in any repository. It is therefore the same KIND of rule as the VCS prune (machine state the repo cannot speak for) rather than the kind this ADR deleted, and `node_modules` and every other project-convention entry stays the repo's decision, unsaid by the app. Both rules live on one `filter_entry` predicate in `collect_files` and the same predicate in `completion_dir`, which is what "one visibility engine, not two" (ADR 0035) has always meant.
