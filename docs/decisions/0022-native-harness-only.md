# The native harness is the only harness — the pi integration is fully removed

The desktop's first-generation integration with the external pi harness — the spawned `pi --mode rpc` process (ADR 0009), the env-gated bridge socket channel to the pi-archimedes suite (ADR 0003), the agent registry (with `pi` as the default entry), and the pi-config seeding of the model catalog (ADR 0012) — is **fully removed**. The desktop is now **only the native archimedes harness** (ADR 0011): one harness (the in-process `AgentLoop`), one model source (the Settings providers list, ADR 0014), one config surface (`settings.json`). The external path was a bootstrap and testing vehicle for the native harness; the native harness has proven out, and the user's model set is fully covered by Settings providers.

**What goes:** the `PiRpc` JSONL client, the external session driver path, the gate/tools extension install, the bridge socket channel + `PI_ARCHIMEDES_BRIDGE_*` env handling, bridge-mode subagents and the ADR 0004 `WorkerRuntime` (native subagents already run on the main runtime), the agent registry + `agents.json` + `list_agents` + the frontend agent picker, `seed_from_pi_config` and the `~/.pi/agent/{settings,auth,models-store}.json` readers, and the stored external data (a DB migration deletes the `sessions` rows of the retired pi entry, drops the `messages` table, and drops the `sessions.agent_id` column). The in-process interactive cores the native harness reuses (`todo_apply`, `sudo_run_flow`, `dispatch_params`, `PendingBridge`/`PendingSudo`/`CachedPassword`/`SudoRun`/`RealSudoRunner`) survive in a new `agent/interactive.rs` module; the `bridge-*` wire events and `RpcError` are renamed harness-neutral (`interactive-*`, `SessionError`). `HarnessConfig`'s fields move into `settings.json` (`defaultModel` already exists; `defaultThinkingLevel` and `enabledTools` join it), and the native resolution chain drops the `HarnessConfig` layer (settings → catalog default).

**What stays:** the in-process `AgentLoop` (`agent/harness/`), native sessions + native-native subagents, the in-process permission gate (ADR 0010), MCP, providers, settings, trusted spaces, the `native_messages` table, and — as **data locations, not harness coupling** — the `~/.agents/` + `~/.pi/agent/` (user) and `.agents/` + `.pi/` (Space-walked) discovery roots for skills and Agent definitions: the user's existing files in the pi dirs keep working with zero migration.

## Considered Options

- **A — Full removal, clean break (chosen).** Delete the external path, the registry, the seeding, and the stored external data in one feature; split the four mixed files (`session.rs` / `bridge.rs` / `subagent.rs` / `permission.rs`) so the native code stands alone; rename the surviving "bridge" machinery harness-neutral. The codebase reads as "the native archimedes harness" — matching the stated goal. Consequence accepted: the user's API keys in `~/.pi/agent/auth.json` must be re-entered once in the Settings providers list.
- **B — Keep unresumable rows.** Keep the `sessions` rows + `messages` table of retired pi sessions (visible in history, resume rejected with a clear error). Rejected: the user chose a clean break — the stored pi sessions are a bootstrap-era artifact, and keeping dead schema (`agent_id`, `messages`) forever is a permanent scar for no user value.
- **C — Keep the registry (single native entry) and/or the pi-config seeding.** Minimal churn: the registry stays with one built-in entry; seeding keeps reading pi's config files (zero re-entry friction). Rejected: the registry exists to support *multiple* agents — with one agent it is machinery without a purpose (YAGNI); and ADR 0014 already decided the seeding is "scheduled for removal, after which the Settings list is the sole model source" — keeping it would leave the app coupled to pi's file formats forever, so "only the native harness" would not be true.

## Consequences

- **Stored pi sessions are destroyed** — the migration deletes them (and their `messages` transcripts) on open. This is the hard-to-reverse core of the decision: the bootstrap-era conversation history is gone by design.
- **The Settings providers list is the sole model source** — a user who had a working pi setup must re-enter their providers/keys once (the ADR 0014 surface this was the bootstrap for). The `GET /v1/models` discovery + live metadata refresh (ADR 0012's mechanism, now the only mechanism) is the whole story.
- **The `~/.pi/` directory convention survives as a discovery root** — skills and Agent definitions in `~/.pi/agent/*` and `.pi/*` keep resolving; the "pi" in the path is a location convention, not a harness dependency. (Removing the roots was considered and rejected — it would force a one-time manual migration of the user's files for a cosmetic win.)
- **The pi-archimedes repo is dead code** — a separate repo, out of scope for this one; its suite (`ask`/`sudo_exec`/`manage_todo_list`/`subagent` tools, the bridge listener) has no consumer once the desktop spawns no pi process. Follow-up: archive it.
- **The ADR 0001/0002/0003/0004/0005/0009/0012 files are deleted** (not merely superseded) — the pi generation of decisions is retired wholesale. ADR numbers are append-only: the gaps in the numbering are the record, and the surviving ADRs are not renumbered (renumbering would break cross-references in CONTEXT.md, code comments, and git history). ADR 0011 (the native harness itself) and 0014 (providers in Settings) stand; 0011's "removed in a later cleanup" / "the pi-archimedes suite retires" consequences and 0014's "transitional seeding" framing are updated to mark both done.
- **Rollback is a git revert of the feature** — the code comes back; the destroyed session data does not (the migration is one-way by design).
