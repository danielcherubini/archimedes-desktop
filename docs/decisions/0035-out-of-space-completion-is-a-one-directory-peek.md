# Out-of-Space file completion is a one-directory peek, never a walk of the home directory

The `?` picker could only complete inside the active **Space**. `?README` reached `README.md`, and a token that began `/` was still a **Listing** query: `?/etc/passwd` listed nothing, and `?/` listed every multi-segment path in the Space, because the query was the whole remainder and a bare `/` is a subsequence of every **Space**-relative path with a directory in it. Users reference files that live nowhere near the Space (`~/.config/htop/config`, `~/scratch/design.md`, another repository's source), and reaching them meant typing an entire path from memory. We decided that a token whose first characters are `/`, `~/`, or a Windows drive root switches the picker to **Directory completion**: it lists exactly ONE directory, the one the token names, which is its parent while a last component is still being typed and itself the moment the trailing `/` is, and it never walks outward. This is a SCOPE change and not the repair of a dead key: the absolute token already formed, and already answered, with the Space's files. `~` is expanded in the first position only, by the `skills::home_dir()` helper that already exists for skill and agent discovery.

The shape was forced by one measurement and one principle. The measurement: a **Listing** is walked once per **Space** and cached so filtering stays synchronous, and a dev machine's home directory is two to three orders of magnitude larger than a repository — `~/.cache`, `~/.local/share`, `~/Library/Caches`, `~/.cargo/registry`, every project's `node_modules`. The principle: there is no `.gitignore` above a repository, so a home-wide walk has nothing for ADR 0034's visibility rule to read, and the ONLY way to make such a listing usable is a hardcoded skip-list — reinstating on a larger scale the exact defect ADR 0034 deleted. One directory at a time costs one directory read when the token's directory changes, needs no cap policy beyond the existing one, and needs no new visibility philosophy. It is a reasonable trade because the user knows roughly which folder a file is in; it is not a search, and it does not pretend to be.

## The inserted path is absolute, even though the user typed `~`

Selecting a row inserts an ABSOLUTE path (`/home/daniel/.config/htop/config`); only the picker's DISPLAY is abbreviated back to `~/…`. This is deliberate and it is the part a future reader will question, so: **nothing in this app expands a tilde.** `FsBackend::resolve` joins a relative path onto `roots[0]` and canonicalises, so a literal `~/notes/x.md` resolves to `<cwd>/~/notes/x.md` and `read` fails on a directory named `~`. The alternative — teaching `FsBackend` to expand `~` — puts a new path-normalisation rule on the very seam the **Boundary** is decided at, a seam its own doc comment calls out as *shared by gate and executor so they cannot resolve `..` or a symlink differently*. Adding normalisation there risks gate/executor divergence, which is the failure mode ADR 0030 exists to prevent. Abbreviating in the display layer instead costs one string and touches nothing that guards a boundary.

## Considered Options

- **A home-wide Listing, cached like the Space one.** Rejected above: walk cost, and it forces the return of a hardcoded skip-list.
- **Expand `~` in `FsBackend::resolve`** so short `~/…` paths can go in the draft. Rejected: a normalisation rule on the Boundary seam, for shorter prompt text.
- **A separate sigil (`??`)** for out-of-Space. Rejected: `~` and `/` are already the user's own vocabulary for "not here", and a third prefix teaches a second key sequence for one idea.
- **Raw `read_dir` out of Space instead of the `ignore` engine.** Rejected: it would need its own `.git` guard and would give the two modes different opinions about what a directory contains. Reusing `collect_files`' flags one level deep means a gitignored `node_modules/` stays hidden in someone else's repository too, and a `.git/` inside a listed directory is pruned by the same rule that prunes it in the **Space** (one caveat, stated where it can bite: the prune is an ENTRY rule, so a directory the user names directly is listed even when it is named `.git` — see the Consequences bullet below).

## Consequences

- **`?/` now lists `/`.** Root entries are completable. What it did before is stated in the Decision above, and it was not "nothing": it was a **Listing** query that matched every nested path in the Space, which is why this is a scope change rather than a repair.
- **Directory rows keep the `?`; file rows consume it.** Selection consumes the sigil, so consuming it on a DIRECTORY would end the descent after one level. A directory is not an answer, so its insertion is `?` + path + `/` and the token stays live; a file inserts the bare path plus a trailing space, exactly as `?` behaves today, and that space is what ENDS the token ("enter on a file row inserts the path with the ? CONSUMED and the CASE INTACT").
- **`follow_links(true)` out of the Space only.** The Space walk keeps `follow_links(false)`, where a symlink's invisibility is containment — a symlink must not walk a Space out of itself. Out here we list one level, so there is no cycle to follow and nothing to contain, and symlinks are the norm rather than the exception (`/etc/os-release`, `~/bin`, `~/.local/bin`, most of macOS `~/Library`). It does not widen what the agent may read: `FsBackend` judges the CANONICALISED target, so a symlink pointing beyond the **Boundary** is caught the way `..` already is. A broken symlink yields an error entry, which is swallowed like every other walk error, so broken links are simply invisible.
- **At the `Sandboxed` Beyond-boundary policy the picker lists files the agent cannot read.** No row is filtered by policy and no warning is shown: that would put a second copy of Boundary logic in the renderer, the wrong place. ADR 0033 already established that the picker is a view of the filesystem and not the enforcement point.
- **A space may appear in a token only when that token began `/`, `~/`, or a drive root.** Relative Space queries keep the strict `[a-zA-Z0-9._/-]` charset, because a space in `?foo bar` would eat the rest of the sentence. An absolute token ADMITS spaces, which means prose typed after it is absorbed into the query until a newline. **The safety is NOT that an absorbed tail cannot match a row.** The matcher is a SUBSEQUENCE test over the SEGMENT after the token's last `/`, so the contents of the directory decide. Usually nothing matches, because the tail makes the segment longer than any entry name, and the picker renders nothing. A directory holding `todo list of items.md` DOES match `?~/notes/` followed by the prose ` list of items`: one row renders, and `Enter` inserts it with the prose inside the token. We accept that, because it edits the user's own draft rather than a policy, and because refusing spaces would refuse `~/Library/Application Support`. A `?` in the prose destroys the token outright (`?/etc/pas?x` forms no token at all), which is the same degradation as any other unformable token. Pinned in `ChatStream.test.tsx` on both sides: "an absorbed prose tail DOES match a row when the directory holds a name that contains it" is the counterexample, in a directory whose entries hold spaces, where `Enter` completes the row; "THE COST WE ACCEPT: a `/` in trailing PROSE reads a directory that cannot exist" and "…and that impossible read holds Enter for ONE round trip, then sends" are the other shape, where the tail moves the DIRECTORY, the read finds nothing, and the token goes out as text once the fetch settles. Without the allowance, `~/Library/Application Support/…` and most Windows profile paths are unreachable by descent.
- **The directory the picker reads is the token's DIRECTORY PART, computed from the WHOLE remainder.** `dirPartOfOutsideQuery` slices to the last `/` of the entire text after the `?`, spaces included, so `?~/Library/Application Support/` reads `Support` and not `Library`. An earlier revision cut at the first space, which sent the picker into the wrong directory for exactly the paths this mode exists for, and it was reverted. A trailing `/` therefore always means "list this directory": `?~/notes/` lists `notes`, and so does `?~/notes/ no`, which lists `notes` and filters it on the absorbed prose. WITHOUT that trailing `/` there is no `/` after the last component to cut at, so the read is the PARENT and the prose sits inside the SEGMENT: `?~/notes no` reads `~/` and filters it on `notes no` — measured, `dirPartOfOutsideQuery("~/notes")` is `~/` and it is the same cut that makes `?~/notes/todo list` read `notes` with `todo list` as its segment (both pinned in `skills.test.ts`). Absorbed prose therefore changes WHICH ROWS match, not which directory is read, unless the prose carries a `/` of its own — and then it does move the read, which is the cost the bullet above records rather than a second rule.
- **Drive-rooted absolute paths (`C:/…`) are admitted for exactly this reason.** The initial plan was to leave `:` out of the charset and treat Windows drive paths as a documented gap; that was wrong, and a plan review caught it. `~/` on Windows expands to `C:\Users\you`, so the absolute path a DIRECTORY row inserts is `C:/Users/you/…`, and if `:` is unformable the kept-`?` token dies after ONE level of descent, on a platform this app ships on, invisibly to ubuntu-only CI. A drive root is therefore part of the absolute token shape (`(~?\/|[A-Za-z]:\/)`), and `expand_completion_root` accepts it.
- **A Windows drive root is REFUSED on Unix and macOS.** `expand_completion_root` returns NOTHING unless the expansion is ABSOLUTE. The byte test above says a query only LOOKS like a drive root; the platform's own `Path` says whether it is one, and off Windows it is not. Without the guard, `C:/secret/` on Linux read the process working directory and returned rows whose `insert` claimed to be absolute (both halves measured, and pinned by `expand_completion_root_never_returns_a_relative_path`). A drive query is therefore refused where it names nothing, which is the honest answer, rather than silently resolved against a directory the user never typed.
- **ADR 0034's three axes survive intact.** Its **scope** axis said the **Listing** is Space-only, and that remains true — Directory completion is a different mechanism, not a second Listing, so nothing in 0034 is corrected. It gets a pointer, nothing more.
- **After a directory selection the picker renders nothing for the duration of one fetch, and `Enter` is HELD for that round trip.** Selecting a directory row moves the token to a new directory, the cache key changes, and the catalog serves its EMPTY payload until that directory's read resolves, while the render gate is `rows || note` (ADR 0033's amendment), so neither rows nor a note means no box. This is deliberate and it is the freshness rule doing its job: the rows of the directory you LEFT must never be selectable into a token that no longer names them, so "blank for a moment" is the correct alternative to "stale and insertable". It reads as a blink rather than a dead picker, and the next level's rows arrive with no further keystroke. **The blank window was a hole, and it is closed.** With no row and no note the picker intercepted nothing, so `Enter` during that one fetch put the raw token in front of the model as text. The composer now holds `Enter` for exactly that one round trip when an absolute token is pending, and holds it for nothing else: a read that comes back EMPTY or REJECTED counts as SETTLED, so a directory that cannot be read never holds `Enter`, and a pending relative (Space) query still sends, because its catalog resolves synchronously ("a RELATIVE ?query with no rows still sends on Enter while a completion fetch is in flight", "the in-flight gate holds ONLY the token under the caret, never another ? token", and "…and that impossible read holds Enter for ONE round trip, then sends", all in `ChatStream.test.tsx`). **What that held window now costs:** the fetch it waits for scans the WHOLE directory — the early `break` was removed so that the cap could be decided over everything the directory holds — so a huge directory is also a longer held keystroke, measured at ~108 ms against ~37 ms for a 55,000-entry directory and ~280 ms at 100,000 (both cost axes, and the reason the memory half of that sentence did NOT change when the `break` did, are in `completion_dir`'s own comment). The `break` remained the wrong trade: it bought its time by deciding which rows EXISTED according to where the alphabet happened to put the directories. And the window is one per DIRECTORY, not one per keystroke — the cache key is the directory, so typing inside a directory that is already read never re-opens it.
- **A capped directory keeps every DIRECTORY and fills the rest with files.** `completion_dir` lets directories claim their slots first (`dir_keep = dirs.len().min(cap)`) and gives files what is left, and `truncated` is computed from that arithmetic rather than from the early `break` this function used to have. Directories are how this mode MOVES, so a directory whose first entries are all files used to render a picker with no way down. Files fill what is left, and when the directories alone exceed the cap the cap is honoured anyway with the excess reported as truncated (`completion_dir_keeps_every_directory_when_the_directory_exceeds_the_cap`, `completion_dir_keeps_the_first_cap_directories_when_directories_alone_exceed_the_cap`, and `completion_dir_reports_truncation_when_only_directories_are_dropped` — added because every earlier fixture that dropped a directory ALSO dropped a file, so the files half of `truncated` was carrying the directories half and the whole suite stayed green with the directories' term mutated away). Directories lead the order only because the walk yields them first, which is why the cap test asserts the raw `read_dir` order is not sorted.
- **A name the token grammar cannot carry is refused, in both walks.** `name_is_completable` rejects a NAME holding `?` or a newline, and it runs as a prune, so a DIRECTORY with such a name is not descended into either. This is REPRESENTABILITY, not visibility: it asks whether a name survives a round trip through the composer, not whether the user may see it. It consults no convention, no project policy and no name-based list, so it is not the skip-list ADR 0034 deleted, and it decides by the GRAMMAR rather than by the catalog, which is where this ADR puts every other scope rule. Without it, a file named `notes?draft.md`, or a name holding a newline, produced a row that formed no token once inserted and could not be continued. Pinned for both walks by `collect_files_refuses_names_the_token_grammar_cannot_hold` and `completion_dir_refuses_names_the_token_grammar_cannot_hold`.
- **Leaving a directory evicts it, so coming back reads it again.** The same eviction rule the Space catalogs use applies per directory: re-entering one you walked away from re-lists it rather than serving the rows you left behind. That is the freshness half of the trade (a directory created or renamed on disk mid-session must show up), paid for with one extra directory read — never a walk, so the cost stays bounded by the size of a directory (`a_key_change_serves_empty_files_until_the_new_listing_resolves_and_evicts_the_left_key` is the Space half; `a_dir_prefix_change_serves_empty_until_the_new_dir_resolves_and_evicts_the_left_dir` and `a_late_response_for_a_left_dir_is_not_applied_even_after_coming_back` are this one, all in `useMentionCatalogs.test.ts`).
- **The reach exception now applies outside the Space, and it reaches further than `.ignore`.** The peek reads its rules from the queried directory AND its ancestors, so an out-of-Space listing is decided by rules the user cannot see in that directory. Two things follow. A `.gitignore` in a PARENT of the queried directory DOES apply, which is the half of ADR 0034 that reads as a contradiction until its own wording is read: that rule is about a **Space** opened AT a repository root, and a queried directory can sit arbitrarily far below its repository. And the nearest ancestor holding a `.git` is the git ROOT of the read, so an ancestor repository's `.gitignore` AND its `.git/info/exclude` both decide the peek. On the common layout where `$HOME` is itself a dotfiles repository, `~/.gitignore` and `~/.git/info/exclude` decide every `?~/…` listing, silently, with `truncated` false and no note in the picker. Nothing above that `.git` reaches in. `core.excludesFile` never does either, which is the one half of this rule NO test backs: `git_global(false)` is unpinnable on CI because pinning it means reading a machine-wide git config, and its code comment says so. This is the same accepted exception ADR 0034 records, now with a wider radius, and it is the price of one visibility rule instead of two (`completion_dir_inherits_an_ancestor_repositorys_gitignore`, `completion_dir_reads_the_nearest_ancestor_repositorys_exclude_and_stops_above_it`).
- **A directory named `.git` is listed when it is the one you asked for.** The VCS metadata prune is an ENTRY rule at depth greater than zero, so no row ever offers `.git` and no `.git` subtree is ever walked as a descendant, but the QUERIED directory's own name is never a prune decision: `?/repo/.git/` lists `objects`, `HEAD` and `config`. Refusing it was considered and rejected. The prune is a rule about what a directory CONTAINS, a **Space** opened at `.git` has always listed it, and the two modes would otherwise disagree about one directory. No row offers `.git` and no hint invites it, so reaching it takes deliberate typing (`completion_dir_lists_a_directory_named_git_when_it_is_the_one_queried`, `completion_dir_never_offers_the_vcs_directories`).

## What is refused, what is accepted, and what is unverified

REFUSED BY CONSTRUCTION, so no code path can produce it: `~otheruser`, because the root requires `~/` and the relative charset has no `~` (supporting it would invite a walk of `/home`); a backslash as a path separator, because the token grammar carries `/`; a Windows drive root on a platform that has no drives, because `expand_completion_root` returns nothing unless the expansion is absolute.

REFUSED BY THE REPRESENTABILITY FILTER, because the token cannot carry the byte: a name holding `?` or a newline, as a file or as a directory, and such a directory is not descended into. An earlier revision of this ADR listed those two bytes as an accepted gap; they are not a gap any more.

ACCEPTED BECAUSE NOTHING IS MISSING: `..` is not a traversal gesture this mode lacks. An absolute query passes `..` to the OS untouched (measured: `?~/../` lists the PARENT of the home the client supplied, through `<home>/../`), a relative token is a query over Space-relative paths so `..` there filters rather than moves, and no `..` ROW exists because the way up is editing the token.

ACCEPTED GAPS, each a consequence of a rule we keep:

- **A name containing `\` or a byte that is not valid UTF-8 is offered out of the Space with a LOSSY insert.** Names are converted with `to_string_lossy`, so such a file reaches the draft carrying the replacement character, and the path in the draft names a file that does not exist (`completion_dir_offers_a_non_utf8_name_with_a_lossy_insert` pins that rather than pretending it away). The `\` half is legitimate and is kept deliberately: `\` is a legal POSIX filename character, so `completion_dir_offers_a_name_containing_a_backslash` insists the row EXISTS, and the absolute token's charset carries it into the draft. Neither byte survives the **Space** side, where the relative charset `[a-zA-Z0-9._/-]` holds neither, so a **Listing** row for such a name arrives already untypeable.
- **A completed path can hand the Mention grammar new material.** Expansion is verbatim and preserving, as this ADR says of its own accord, and `@` or `#` is recognised wherever the glyph follows whitespace or a line start. A file named `notes @draft.md`, once COMPLETED, therefore expands a real `@draft` block on send if a resource of that exact name exists. It is pinned as intended-and-observed rather than as a defect ("a completed path containing ' @<catalog agent name>' DOES expand that Mention on send"), because refusing it would mean sanitising an inserted path, which is the same path-versus-content line ADR 0033 draws.
- **Policy does not filter rows.** At `Sandboxed` the picker lists what the agent cannot read, and the composer enforces no policy, so a refusal there would be a second copy of Boundary logic in the renderer.

UNVERIFIED, and not quietly: Windows paths (drive roots, the `C:\Users\…` expansion, `\` in names) are reasoned about and pinned wherever the platform allows, but CI runs ubuntu, so no Windows filesystem has ever executed this code. The roadmap's manual smoke is the only end-to-end check that exists, and it stays open until someone runs it.
