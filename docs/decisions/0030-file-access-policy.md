# File access is a per-direction policy the user chooses — and the default is "Don't ask me"

Before this, file access had exactly one setting and the user did not own it: the path-param tools were hard-confined to the **Space**'s `cwd` by `FsBackend` (ADR 0011) and `bash`/`edit`/`write` prompted on every call unless the Space was trusted (ADR 0010). Both halves were wrong in opposite directions — a **trusted** Space still could not write one file outside its folder, and an untrusted one was interrupted for every command. We decided: three independent policies — `reads` / `writes` / `shell` — each one of `AccessPolicy { Sandboxed, Ask, Allow }` (**`Allow` is the default for all three**), judged against a per-**Session** **Boundary** that is a *set* of directories rather than the `cwd` alone, in one pure decision point (`agent::policy::decision_for`) that the `AgentLoop` consults before dispatch. `Sandboxed` means *refuse* for a path-param tool and *confine* for `bash` — the latter a real Landlock ruleset installed in the spawn's `pre_exec`, Linux-only, fail-closed.

**The default is a widening, chosen deliberately.** Out of the box an Archimedes agent reads, writes, and runs commands anywhere on the machine, with no prompt and no denial. That is pi's posture — pi has no tool-level containment and no built-in approval gate at all, and draws its isolation line at the *process* instead (ADR 0029 records the same finding for skill reads) — and the desktop ships a coding agent, not a sandbox people have to unlock before using. It is also the honest default for the feature's own value: today even a fully trusted Space cannot write outside its `cwd`, because `FsBackend` rejects the path before any gate runs, so `writes = Allow` is the *first* way to write outside the Space at all. See **Considered Options** for why we did not default to today's behavior — the cost is stated in **Consequences**, because it is the most consequential line in this ADR.

## The truth table

`beyond` means "the resolved path is outside EVERY root of the direction's Boundary"; for `bash` there is no path to judge, so the caller passes `beyond = true` unconditionally — a command can reach anywhere (`policy_verdict`, `harness/loop.rs`).

| Policy | Inside the boundary | Beyond, untrusted | Beyond, trusted |
| --- | --- | --- | --- |
| `Sandboxed` | allow | **deny** (path tool) / **confine** (`bash`) | same — trust changes nothing |
| `Ask` | allow | **prompt** (`permission_title` names the thing) | allow (suppressed) |
| `Allow` (default) | allow | allow, silently | allow, silently |

**Precedence: Trust suppresses prompts but never widens a deny.** That one rule is what the three interacting mechanisms (policy / trust / boundary) hinge on, so it is asserted directly in `policy.rs` rather than left to fall out; the `Sandboxed` arm does not read `trusted` at all. A denied access therefore never reaches the UI in any configuration — a `Deny` is a tool-result error (`deny_tool_result`), worded identically to the executor's own rejection so the model's recovery behavior cannot depend on which layer said no.

**The boundary is a root set, seeded asymmetrically** (`agent::boundary`). It has to be a set: `skills::space_roots` walks UP from the `cwd` to the repo root, so for `cwd = /repo/packages/app` the root `/repo/.agents/skills` is outside the session `cwd` yet must be readable — and the user-level discovery dirs are outside every session by definition. `read_roots(cwd)` = canonical `cwd` FIRST, then the user- and space-level skill/agent discovery roots; `write_roots(cwd)` = the canonical `cwd` ONLY. The asymmetry is the point: reads are granted the agent dirs because **ADR 0029**'s problem was precisely that the sandbox could not reach them, while writes are not, because a model that can rewrite `~/.agents/skills/*/SKILL.md` rewrites its own instructions for every future session. Space-level `.agents/`/`.pi/` dirs are repo content and stay writable as descendants of a repo-root `cwd`; `roots[0]` is always the canonical `cwd` because it is what a relative path joins to. Containment itself is not reimplemented — it is ADR 0029's canonicalize-then-check (`FsBackend::validate`), shared by gate and executor so the two cannot resolve `..` or a symlink differently, which is the classic escape. An EMPTY root set is an error, never "no limits".

## The write floor

Reads are gated *by the boundary*; the executor is **unrestricted** at `Ask`/`Allow` (`boundary::executor_roots` → `[cwd, UNRESTRICTED]`, where `UNRESTRICTED` is `"/"`), because a read the gate just approved, or prompted for and received, must actually land — an `Ask` whose approval then fails on a sandbox check is a prompt that lied. Writes accept anywhere on the machine at `Ask`/`Allow`, **except** the four user-level dirs — `~/.agents/skills`, `~/.pi/agent/skills`, `~/.agents/agents`, `~/.pi/agent/agents` (`boundary::protected_dirs`) — which are refused in **every** policy, as a deny, never a prompt, never widened by Trust (`protected_refusal_text`, consulted before the boundary so the refusal states the true reason). **This is a guard-rail, not a security boundary**: `shell = Allow` (the default) writes those files with `bash` in one command, and Landlock cannot express "anywhere except these dirs" because it is allow-list-only, so at `Sandboxed` they are simply absent from the allow-list.

**`Sandboxed` refuses paths but confines `bash`, and that asymmetry is not an oversight.** For `read`/`write`/`grep` the boundary *is* the refusal — there is nothing to confine, so `Decision::Confine` is unreachable for a path tool (asserted exhaustively). For `bash` a refusal would mean `Shell = Sandboxed` disables `bash` entirely, and confining is exactly what the user selected. `sh -c` cannot be path-parsed (`cat $(echo /etc/pa$$)`), so the process is the only thing that can be honestly constrained.

**Considered Options**

- **Deliver the policy on `StartEnv` / the `Config` frame** (push it from the Client when the setting changes, like the trust flag): rejected — it costs a new `from_parts` argument threaded through every Worker-construction site (`protocol.rs`, plus the session-manager and `fake_worker` call sites), another positional `AgentLoop::new` argument at all six of its sites, a new field on the existing `Inbound::Config` frame, and a global settings-relay that `send_config_to_space`'s cwd filter cannot express — **all to move a file the Worker already reads.** ADR 0025's Worker is a config *reader*, not a config *recipient*: `mcp/manager.rs` reads `settings.json`'s `mcpServers` inside `AgentLoop::new` and `harness/launch.rs` reads `subagentModels` per dispatch, with the comment "a settings edit takes effect on the NEXT dispatch, no restart". Policy rides the same file the same way (`load_settings(config_dir).file_policy`, once at the top of `handle_prompt`). Accepted costs, recorded because they are real: freshness is **per turn** (a mid-turn edit is observed at the next prompt — one read per turn, so every tool call in a turn agrees and a half-asked batch can never reflect a policy the user never chose); a corrupt or missing `settings.json` yields all-`Allow`, which is the shipped default rather than a new widening, but does mean the policy file is not authenticated by the desktop; `config_dir: None` (tests, any loop without a desktop layer) means all-`Allow`. Subagents inherit for free — the child env carries the parent's `config_dir`.
- **Default to today's behavior** (`Sandboxed` / `Sandboxed` / `Ask`): rejected — it would ship a feature whose out-of-box state is the state the user already had, keep the trusted-Space-can't-write-outside defect, and make the desktop the only coding agent in this family that needs configuring before it is useful. Rejected *knowing* the cost: the default is the widening described above, and it is the reason ADR 0010 changes meaning (below). A compromise — `Ask` for `writes`/`shell` only — was rejected too: a default that prompts on every `edit` in a repo the user opened is the interruption pattern this feature exists to make optional, and the Settings copy is where the free pass is disclosed.
- **Per-Space policy** (a policy column beside the Space's `trusted` flag, ADR 0010's storage): rejected for now — three selects are the whole product today, and per-Space policy multiplies the states of an already three-mechanism model (policy × trust × boundary). Recorded as a deliberate limit, not an oversight; nothing in the shape of `FilePolicy` blocks it later.
- **One policy for all three directions**: rejected — the directions genuinely differ in risk and in what the user wants (reading a `README` in a sibling package is not writing `~/.bashrc`), and the read/write split is what lets the read boundary include the agent dirs while the write boundary excludes them.

**Consequences**

- **ADR 0010's untrusted-Space prompt is now opt-in.** `shell`/`writes` = `Ask` restores it; at the shipped default nothing prompts on an untrusted Space, so opening an untrusted repo does out of the box what opening a trusted one always did. The gate is no longer keyed on a hardcoded list of mutating tools — `MUTATING_TOOLS` is deleted and the prompt decision is `decision_for`'s verdict. This ADR does **not** supersede 0010 — trust still means exactly what it meant there, *suppress the prompt* — it removes 0010's premise that a prompt is always there to suppress. Trust remains stored per-Space, desktop-enforced, and fail-closed.
- **ADR 0011's "tools are sandboxed to the Space's `cwd`" is narrowed, not replaced.** The `cwd` is one root of a set, and the set is enforced only at `Sandboxed`. 0011's architecture stands (the desktop is the harness, `FsBackend` is the containment seam); 0030 makes the seam's root set and its activation policy-owned. No `superseded-by` — a narrowing that keeps the original's decisions intact.
- **Policy lives in `settings.json` (`filePolicy`), so it is global, not per-Space, and per-turn, not live.** The Settings write and the Worker's read are the same file, which is why there is no new wire surface at all — and why a hand-edited `settings.json` is an accepted input, exactly as a hand-edited `mcpServers` already is.
- **Fail closed is the product stance: breaking the feature beats breaking the promise.** `Shell = Sandboxed` with no Landlock does not run the command unsandboxed — the spawn fails with `"Sandboxed shell is unavailable: <reason>"` (or `"… on this platform"` off Linux, where `tools/sandbox.rs` is not compiled at all), and the Settings grey-out (`shell_sandbox_available()`) and that path (`Sandbox::create`) rest on the same kernel ABI probe — `create` re-probes it and additionally fails on a required rule path it cannot build — so a kernel without Landlock is never offered as a tier. Likewise an unjudgeable path is `beyond`, never allowed, and an empty root set means nothing is in bounds.
- **The sandbox's promise is "confined to your project" plus the paths a usable shell needs, and never "isolated".** Measured on the test kernel (7.2.8-200.fc44, Landlock ABI 10): with `Shell = Sandboxed`, `echo x > ~/outside.txt` fails `EACCES` and so does reading a file outside the allow-list — `READ_FILE` is HANDLED, so the ruleset confines the child's reach into your files **including reads**, not merely writes and directory enumeration. What is readable *by design* is the system dirs (`/usr`, `/bin`, `/dev`, `/proc`, the loader paths) and a named list of `/etc` resolver/CA files — a `bash` that cannot `ld.so` or resolve a name is not a shell — and `/tmp` and `/var/tmp` are writable by design, so "confined to your project" is the shorthand, not the literal rule set. There are **no network rules at any ABI** (`handled_access_net` is 0; Landlock's own network rights arrive at ABI 4 for TCP and ABI 10 for UDP and this tier uses neither), so a confined command can still `curl` out with anything it was permitted to read. It is still **tighter than the write tools' `Allow` floor**, which accepts anywhere on the machine. And it applies only to the policed tools: `sudo_exec` and the MCP tools sit outside the policy (`POLICIED_TOOLS` is `bash`/`read`/`find`/`grep`/`ls`/`write`/`edit`), so `Shell = Sandboxed` confines `bash` and nothing else. The Settings copy states these limits next to the select rather than leaving them to the module doc.
- **`Don't ask me` is silent and unlogged** — no prompt, no `permission-request` event, no record of an out-of-boundary access. That was already true of a trusted Space's auto-approved calls (ADR 0010); it is now true by default, which is the honest answer to "what did the agent touch" being unanswerable at the default settings.
- **`read_skill` / `list_skills` stay outside the policy** (`POLICIED_TOOLS` lists `bash`, `read`, `find`, `grep`, `ls`, `write`, `edit` and nothing else): they take a skill NAME and keep ADR 0029's per-skill containment, so the session boundary is not their judge and a `Reads = Sandboxed` session can still load a user-scope skill. That is the one path ADR 0029 exists for and it must not be "unified" into the policed set — a `read_skill` that gained a path parameter is exactly what would make it escapable.
- **The macOS `sandbox-exec` profile is deferred, as a decision.** The native harness is Linux-only today (`tools/exec.rs`: "`powershell` is deliberately absent (Windows-only; the harness is Linux-only)"), so a Seatbelt profile would be untestable dead code. Non-Linux platforms **hide** the Shell `Sandboxed` tier (Windows and macOS identically — there is nothing to choose), and the profile lands with macOS native sessions. `Ask` and `Allow` work everywhere; only the `Confine` tier is platform-bound.
- **Three mechanisms interact by design and that is the accepted complexity budget** — policy (what the user chose), trust (whether a prompt is worth showing), boundary (what counts as far). Chosen for shipping speed over one unified model; the price is that readers must learn the precedence rule above rather than derive it, which is why it is stated in one sentence, asserted in `policy.rs`, and repeated in `CONTEXT.md`.
