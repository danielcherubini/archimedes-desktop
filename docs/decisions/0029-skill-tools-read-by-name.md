# Skills are read by NAME through dedicated tools, not through the sandboxed `read`

The system prompt advertised every skill's absolute `<location>` and told the model to "use the read tool to load a skill's file" — but `read` is sandbox-validated against the session `cwd` (ADR 0011), and **user-scope skills live outside it** (`~/.agents/skills`, `~/.pi/agent/skills`). So for every user-level skill — most of them — the instruction was unsatisfiable by construction: `read: path escapes the session sandbox`. The only working path was a gated `bash cat`, which burns a permission prompt per skill load or fails outright in an untrusted Space. We decided: two new harness tools — `list_skills` (the catalog) and `read_skill` (a skill's `SKILL.md` body, or a file bundled with it via `path`) — resolve skills by **name**, never by model-supplied path, and `<available_skills>`' instruction lines point at `read_skill` instead of `read`/`bash`.

**This is a self-inflicted mismatch, not a pi divergence.** pi ships NO skill tool and needs none: its `read` has no containment at all (`dist/core/tools/path-utils.js`'s `resolveToCwd`/`resolveReadPath` resolve + expand `~` and read; no root check, no approval hook), so pi's "Use the read tool to load a skill's file" is a TRUE instruction there. pi draws its isolation boundary at the PROCESS instead (`docs/containerization.md`: Docker / Docker Sandboxes / OpenShell / Gondolin — never a path-parameter check inside a tool). The desktop ported pi's `formatSkillsForPrompt` verbatim (ADR 0017) but had already invented tool-level containment in `FsBackend` (ADR 0011: "tools are sandboxed to the Space's cwd") — importing an instruction whose precondition pi provides and we do not. **Read the exception correctly:** `read_skill` is dramatically NARROWER than pi's equivalent read surface — pi reads any absolute path ungated; `read_skill` reads only files inside a discovered skill's own directory, keyed by a name from a catalog the prompt already printed. It restores pi's capability without adopting pi's permissiveness.

**Why:** the sandbox boundary is correct and must not move. A skill is desktop-owned configuration (ADR 0013) that the Client already reads and advertises; it is not session data, and the honest fix is a tool whose *allowlist is the discovered skill set*, not a widened filesystem view. Because `name` must match a discovered skill, no arbitrary path is ever reachable — the tool adds no read surface at all (`SkillInfo.body` is already read and parsed by discovery). A skill's bundled files (`./adr-format.md`, scripts) are reached by a **per-skill `FsBackend`** rooted at that skill's directory: `..` traversal, absolute paths, and symlinks out of the dir are rejected, and a sibling skill's files are NOT reachable — the boundary is the skill's dir, not the skill root.

**Considered Options**

- **Gate instead of sandbox for out-of-sandbox reads** (make `read` CONFIRM a path outside the cwd rather than reject it — the repo's own `bash` pattern: "GATED, not sandboxed", and pi's permission-extension model, `docs/extensions.md`: a `tool_call` handler decides what to confirm): rejected — a permission prompt per skill load is the exact pain being fixed (and it fails outright in an untrusted Space), and the gate is coarse: one "yes" opens EVERY absolute path for the session, so it trades the discovered-set allowlist for a blanket grant. The narrow tool is both less friction AND less surface.
- **Adopt pi's model wholesale — drop tool-level containment and isolate at the process** (ADR 0011's boundary, containerized like pi's `docs/containerization.md`): out of scope here — the desktop's sandbox is a shipped product decision (ADR 0011) and this change does not revisit it; `read_skill` is compatible with adding process isolation later.
- **Widen `FsBackend` with read-only extra roots (the skill roots)**: rejected — it makes `read`/`grep`/`find`/`ls` all read into `~/.agents/skills`, exposing every file there (arbitrary user data, notes, scripts) rather than the advertised skill files, and it permanently loosens the one boundary ADR 0011 defines.
- **Drop the absolute `<location>` from `<available_skills>` and advertise only `<name>`**: rejected — the path is still genuinely useful (a `bash`-only session, `cd`-ing into a skill dir to run its scripts), and keeping it preserves pi's `formatSkillsForPrompt` shape, which this prompt is a port of. The temptation to make the doomed call is removed by changing the *instruction line*, not by hiding the path.
- **Leave bundled files to gated `bash`** (`read_skill` reads only `SKILL.md`): rejected — several installed skills bundle references (`discuss` → `adr-format.md`, `context-format.md`); they would stay half-broken, loading their instructions and then failing on the first relative link.
- **A single gateway tool (`read_skill` with an optional `name`)**: rejected in favour of two explicit tools — `list_skills` is the obvious name to the model and matches the `list_agents` precedent (ADR 0020); the extra spec is ~60 tokens and the parent rarely needs it (its catalog is already in the prompt), but the child semantics stay unambiguous.

**Consequences**

- **The sandbox rule now has a documented, narrower exception.** `exec.rs`'s module doc states it: `bash` is gated-not-sandboxed, the path-param tools are sandbox-validated, and the skill tools are name-keyed against a discovery allowlist. A future reader must not "unify" `read_skill` into `read` by adding a path parameter — a path parameter is exactly what makes it escapable.
- **The `list_skills` name collides with the Tauri IPC command `list_skills`** (the left-pane catalog, `commands/skills.rs`) — the same accepted precedent as `list_agents` (ADR 0020): model tool vs Client IPC, different layers, no runtime collision. Do not "unify" them.
- **The tool's catalog cannot drift from the prompt's catalog**: both go through the same `skills_for` → `discover_skills(Some(cwd))` call, and `ToolCtx::skill_roots: Some(_)` pins explicit roots purely as the test seam (mirroring `skills::discover_in_roots`) so no unit test ever reads the real `~/.agents/skills`.
- **`<skills>` is now advertised when `read_skill` is present even if `read`/`bash` are not**; `read_skill` wins the instruction line over both. The `read`/`bash` lines remain as the fallback for a session whose tool set excludes `read_skill` (a Space-scope skill inside the sandbox still loads there; a user-scope one genuinely fails — the pre-existing behavior).
- **A subagent child still gets no `<skills>` section** (`build_child_system_message` is intentionally reduced, ADR 0017), so a child sees no catalog and must call `list_skills` itself if it needs one. That is a separate, unfixed gap — `read_skill` is advertised to children (only `subagent`/`list_agents` are stripped), so the capability is there and only the advertisement is missing.
- **A rejected `read_skill` path must NEVER surface the `FsError` verbatim.** `FsError::PathEscape` carries the **canonicalized** path, which for a symlink inside the skill dir is its target OUTSIDE it — information the model never supplied (it named only `link`). Echoing it, as `read` harmlessly does for a path the model itself passed, turns a repo-shipped skill (`data.txt` → `~/.ssh/id_rsa`) into a **path-disclosure oracle**. `exec_read_skill` matches `PathEscape` explicitly and names only what the model sent plus the boundary it already knows; `Io` failures (nothing foreign is named) pass through. Do not "improve" the message by re-appending `{e}`.
- **The boundary is adversarially tested**, not just reasoned about: `src-tauri/tests/skill_tools_boundary.rs` attacks the per-skill `FsBackend` with `..` traversal, absolute paths, `/`, `.`, `..`, a NUL byte, a symlink to an outside file, a symlink to a sibling skill's file, a DANGLING symlink, and a symlinked DIRECTORY — asserting rejection, no foreign content, and no unnamed-path disclosure for each. It also pins that the NAME (not the path) is the allowlist: no prefix match, no trimming, and a skill in a non-allowlisted root is unreachable even by exact name.
- A bundled file is returned **verbatim** (the file's own bytes), unlike `read`'s line-join — the point is reaching the exact file a skill references. Only TEXT bundled files are readable (`read_skill` goes through `FsBackend::read`, which is `read_to_string`): a skill that bundles an image cannot have it inlined, unlike the `read` tool's image path. Deliberate for now — a skill's instructions are the product, an image is not.
