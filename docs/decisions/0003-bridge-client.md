# Bridge client: env-gated local channel to the agent for delegated UI

The archimedes suite running inside an Agent process managed by the Client needs a way to (a) get the user's answers back into interactive tools (`ask`, `sudo_exec`) and (b) push ambient state (todos, cost, agent state) to the Client. ACP has no agent→client input channel — `session/request_permission` is approve/deny only. We decided the Client speaks a local bridge channel (the suite's **bridge**, see the pi-archimedes glossary and its Decision 0022) and renders the delegated UI itself.

We decided (2026-08, design discussion) on:

- **Opt-in per agent via a registry `bridge: bool` field.** The built-in `pi` entry has `bridge: true`; other ACP agents (no archimedes suite) don't. When set, the Client spawns the agent with `PI_ARCHIMEDES_BRIDGE=1` + `PI_ARCHIMEDES_BRIDGE_SOCKET` (a per-spawn randomized 0600 Unix socket under a 0700 dir; named pipe on Windows) + `PI_ARCHIMEDES_BRIDGE_SESSION=<the desktop's own session id>` + `PI_ARCHIMEDES_BRIDGE_SERVER_PID=<the desktop's own pid>` — NOT the ACP `sessionId`, which is agent-generated in the `session/new` response and does not exist at spawn time — through the existing registry `env` passthrough. The Client starts the listener before the spawn call returns (the push retry window is only ~2 s), unlinks the socket on session close, and tolerates/cleans stale files at startup.
- **The Client is the server; ephemeral connections; peer-verified.** A new `acp/bridge.rs` mirrors `permission.rs`: accept loop reads line-delimited frames; a connection is accepted only if the connecting process is **a descendant of the desktop itself** — the anchor is the desktop's own pid (`std::process::id()`, always alive, so no liveness check is needed), NOT the spawned agent's pid (the ACP SDK spawns the agent internally and does not expose the child pid). The topology is desktop (D) → `pi-acp` (A, a direct child of D, spawned in-process by the SDK) → `pi` (P, a grandchild, spawned by `pi-acp`); the peer connecting to the desktop's socket is `pi` (P). On each connection the desktop reads the peer's pid (`SO_PEERCRED` on Linux, `GetNamedPipeClientProcessId` on Windows) and walks the parent chain up to the desktop's own pid (Linux `/proc/<pid>/status` `PPid`, bounded ≤8 hops; Windows Toolhelp snapshot) — if the chain doesn't reach the desktop's pid, **reject the connection** (fail-closed). The spawned child's exit tears the listener down + unlinks immediately (closes the pid-reuse window; Windows: the pipe instance vanishes when the last handle closes — no unlink API). **Platform policy:** the cred-based verification is gated `#[cfg(target_os = "linux")]` — on **macOS** (a bundle target; no `SO_PEERCRED`/`ucred`) the bridge listener is **not started** (fail-closed, documented v1 limitation). **Agent→Client (Windows, v1 limitation):** the agent-side `GetNamedPipeServerProcessId` check is a **documented v1 limitation** (Node's `net` exposes no such API — it would need a native addon); in v1 the agent presence-checks `PI_ARCHIMEDES_BRIDGE_SERVER_PID` only, and the desktop-side descendant check is the real defense. The desktop creates the **first** pipe instance with `FILE_FLAG_FIRST_PIPE_INSTANCE` (pre-squat detection) and subsequent listener instances **without** it (so its own concurrent connections work). `{"type":"request",...}` → `bridge-request` Tauri event + oneshot sender in a `pending_bridge` map keyed `"{session_id}/{request_id}"` (the `permission.rs` pattern); a spawned waiter writes the reply, caps at **330 s** (agent timeout + 30 s margin, so the agent's cancel deterministically wins), and session-close (and a failed `connect_with`/`session/new`) tears the listener down unconditionally + drains all pending as cancelled — every Client-initiated termination (timeout, drain, auth failure) sends an explicit terminal frame (`error:"cancelled"`) before closing, and **connection close = immediate cancel** of the pending UI + map entry. Push frames get a `bridge-event` Tauri event + an ack line; the Client drops frames with `seq <= lastSeq` (**`lastSeq` scoped per bridge listener / per spawn**; `seq` starts at 1) and coalesces pushes to at most one in-flight connection per event type (latest wins). Unknown push events are ignored (still acked); unknown methods get an `error` response.
- **The UI placement rule.** Conversation → inline card in the stream (`AskQuestionCard` replaces the pending `ask` `ToolCallCard` — keyed by `(source, toolCallId)` or the frame's UUID `id`, never by bare `toolCallId` (cross-process ids can collide); subagent asks anchor by `source` with a labeled card; stacking defined for concurrent asks); security gate → modal (`SudoConfirmModal`, `SudoPasswordModal`); persistent state → side panel (`TodoBoardPanel` right rail). Visuals port the TUI designs (accent separator + circular radio list + footer hints; numbered ✓/◉/○ todo items with right-side subagent columns) in the desktop's existing amber palette. **The double prompt is by design**: the vanilla ACP permission prompt (generic gate, all tools/agents) is followed by the tool-specific bridge modal — the user's explicit choice.
- **The sudo_exec permission prompt stays vanilla.** The ACP permission prompt is a generic gate (works for all tools and agents); the bridge confirm modal is the sudo-specific security gate. Three interactions: permission → confirm → password (two when the credential cache is warm). 0010's guarantees hold on the Client side: the password flows modal buffer → Tauri IPC (in-process) → bridge reply frame (0600 local socket, peer-verified) → `sudo -S` stdin → the **bridge-channel copy is dropped** (the pre-existing in-memory credential cache retention is unchanged — 0010's scope); it never appears in ACP frames, tool results, the SQLite history, **logs, or the `pending_bridge`/store state after the reply is sent** (removed immediately).
- **The todo board works without the bridge.** `TodoBoardPanel` also seeds from the latest `manage_todo_list` `rawInput` (arriving via pi-acp), so the board renders for non-bridge agents too.

Considered and rejected:

- **ACP-only (rich read-only cards from `raw_input`/`raw_output`):** no input channel exists, so interactive tools stay broken; useful on its own but insufficient.
- **A `password` tool parameter or an ACP extension for user input:** puts the credential in the LLM context / ACP wire — the 0010 rejection, restated for the Client.
- **Absorbing the confirm into the re-skinned permission prompt (single interaction):** couples the generic ACP gate to the sudo-specific bridge gate; the user explicitly kept the two surfaces decoupled.

Consequences: the Client gains a second, local, same-user surface for credentials (the bridge socket); its trust boundary is the spawn-env handshake **plus the Client→agent descendant match** (the anchor is the desktop's own pid; the agent→Client `GetNamedPipeServerProcessId` check is a **v1 limitation** — presence-check only) — a 0600 file alone is only a user boundary (a same-user process can read the agent's environ). The descendant match trusts the **desktop's entire process tree** (the `pi-acp` direct child, the `pi` grandchild, and any command the agent executes), so the verification's guarantee is only against non-agent same-user processes; the trust boundary is the desktop's process tree, slightly wider than the agent's (it also covers the desktop's other children), but the desktop only spawns the agent, so the practical widening is nil; a same-user process can unlink the Client's socket and bind its own (fake Client) but gains nothing beyond existing same-user capabilities (the protected direction is password exfiltration), and responses ride the originating verified connection. On **macOS** the bridge is unavailable in v1 (the listener is not started — fail-closed). `state`/`cost`/`session` pushes are stored but not rendered in v1 (status bar / cost display is follow-up). The bridge is inert for agents without the archimedes suite. Downgrade safety: an old desktop never sets the env vars (a new suite stays inert); a new desktop + old suite sets env the old suite ignores (today's behavior).
