# The `?` file completion inserts a path and never injects content, so the agent's policy-gated `read` stays the enforcement point

The composer gained `?<query>` to complete a file path from the active **Space** (`?REA` → `README.md`). It looks like the `$` / `@` / `#` **mentions** and sits in the same picker, so the obvious implementation is the `$` one: resolve the thing, inject what it refers to. We decided NOT to — selecting a row REPLACES the token with the file's path relative to the **Space** (the `?` trigger is consumed), the message carries plain text, and the **Agent** reads the file with its own `read` tool.

**Why:** injecting file CONTENTS from the composer would be a policy the user can type around. The **Beyond-boundary policy** gates the agent's file tools (`policy::decision_for` over `boundary::read_roots`, ADR 0030), but the composer is the USER's hands and already reads arbitrary paths today (the `+` picker's `read_file_bytes`). A user who set `Reads = Ask` or `Sandboxed` to lock a session down could have any file pasted into the prompt by the Client with no policy consulted and no **Permission prompt**. Completing a path keeps ONE enforcement point — the agent's `read`, which IS Boundary- and policy-gated — and the user gets the prompt they asked for.

**Considered Options**

- **Inject the contents like `$` does for a Skill**: rejected — the bypass above, plus it needs a size cap and a text-attachment concept that does not exist (Attachments are images-only, ADR 0008).
- **Allow `~` and absolute paths** (the original sketch was `?~/.bashrc`): rejected for v1 — Space-only scope means the picker walks only the canonicalized **Space** the user already opened, adding no new read-anything surface and no home-expansion semantics the codebase does not have. `$`/`@`/`#` already reach user-level resources, so this is a narrower affordance by choice, revisitable.
- **Refactor `exec_find` to share one walker with the picker**: rejected — `exec_find` gets its speed from shelling out to `fd` with a per-directory glob fallback; a picker runs on EVERY keystroke, so sharing means either a subprocess spawn per keystroke or a slower agent `find`. The two are cross-referenced by comment instead, the discipline recorded for the mirrored `parse_value`.
- **A `filePolicy`-style toggle for `?`** (as ADR 0032 did for `#`): rejected — `#` collides with pasted code (`#include`, `#123`); `?` has no such class once it requires ≥1 path char, which is what keeps `??` (git porcelain) from opening the picker and turning Enter into an insertion instead of a send.

**Consequences**

- **`?` is not a Mention and must not be made one.** It has no `MentionKind`, no block, no chip, and `expandMentions` / `splitMentionBlocks` / `mergeDedupeKey` never see it. Be precise about what that buys, because the sentence we wrote here first was too strong: **`?` introduces no TAG of its own** — an inserted path is ordinary message text, and as text it is subject to the mention grammar **exactly like text the user hand-typed**: a path containing `$name` (at ANY depth — `$` is boundary-free on the left per ADR 0031) or a root-level `@name` / `#name` CAN expand into a block when a resource with that exact name exists (the picker's `fuzzyMatch` is a SUBSEQUENCE match, so `?src/rea` offers a real `src/$read.md`, and a skill named `read` then expands it). That is a **pre-existing property of the grammar, not a new surface of `?`**: the identical draft typed by hand produces the byte-identical result, so `?` adds convenience, not capability — and it is no tag injection and no policy bypass either, since the interpolated name is still exact-matched from the catalog, which is what keeps ADR 0031's tag-safety argument intact. `skills.test.ts` pins this ("an inserted path obeys the mention grammar like hand-typed text"), so narrowing the grammar to prevent it stays a CONSCIOUS decision rather than a silent side effect. Separately: the reason `?` PRESERVES CASE (`?REA` → `README.md`, not `readme.md`) is that the insertion is VERBATIM — no lowercasing rule applies to a path — NOT that nothing re-matches it; its charset likewise takes `.` `_` `/` and uppercase. Both are deliberate divergences from the mention grammar; do not "unify" them.
- **ADR 0031's "if matching ever becomes prefix/fuzzy this collapses" tripwire is about EXPANSION matching, and expansion stays exact** (`name.toLowerCase() === token`). The `?` picker's `fuzzyMatch` filters file PATHS to decide which rows to SHOW, and a path never interpolates into a tag — so `?` neither arms nor weakens that tripwire. (Stated here rather than in 0031 because that ADR is merged, hence append-only.)
- **A new Client-side filesystem surface exists**: `list_space_files(spacePath)` walks the canonicalized **Space** (cap 5,000, dot-dirs and `node_modules` skipped, `truncated` reported), which is strictly narrower than the `read_file_bytes` capability the Client already has and than what the agent's own `find` / `ls` do each turn. The Client still reads no file bytes on `?`'s account.
- **The picker's data is now partly async**, which is safe for a reason worth keeping: an empty `filtered` means no picker renders and the keyboard branches stay inert, so Enter still sends while a listing is in flight — the same degradation ADR 0032 relies on. Any future prefix must preserve that property rather than block the send.
- *Partial: see ADR 0034 (2026-10-09).* Two clauses above were later narrowed, and only two. **(1) The listing's name rules:** neither skip above is an app rule of the shape described any more, in two different ways. `node_modules` is not skipped by an app skip-list at all — the repository's own ignore rules decide that (ADR 0034). And the blanket dot-directory prune went too, narrowed at `2e63869` to the VCS metadata directories — `.git`, `.hg`, `.svn`, at any depth, DIRECTORIES only — so `.github/` and `.vscode/` ARE listable while `.git/` still never is. What the app keeps is exactly the machine state no ignore file can ever speak for, because `git` cannot ignore its own `.git/` (see 0034's "The one app rule the repo cannot override"); the dot-FILE half of the sentence above survives untouched, which is why `?.env` and `?.gitignore` still complete. **(2) The async clause above:** an empty `filtered` no longer means NO picker renders — the render gate is `open && (filtered.length > 0 || note)`, so a `note` alone renders the box over an empty row list, which is exactly the capped-listing case the note exists for. The safety that clause was protecting is intact: every keyboard branch still gates on `filtered.length > 0`, so Enter still sends. The rule to carry forward is "empty rows ⇒ no selectable rows and Enter still sends; a note may still render the box" — not the stronger sentence. Everything else here stands, above all the decision in the title — `?` inserts a PATH and never injects content, so the agent's policy-gated `read` stays the ONE enforcement point — which is why this is a narrowing, not a `superseded-by` (the convention ADR 0030 records for ADR 0011: "No `superseded-by` — a narrowing that keeps the original's decisions intact").
- *Partial: see ADR 0035 (2026-10-09).* One CONSIDERED OPTION above was REVERSED, and only that one. **"Allow `~` and absolute paths" is now shipped**, so two of its clauses no longer describe the picker: `~` is in the `?` charset (expanded in the FIRST position only, and never for another user — `~otheruser` cannot form a token), and a `/`-, `~/`- or drive-rooted token is not Space-only any more — ADR 0035's **Directory completion** lists exactly ONE directory for it. Two of this ADR's own reasons survive the reversal and are worth restating rather than rediscovering. (1) "Space-only scope means the picker walks only the canonicalized **Space**" named the MECHANISM that kept v1 narrow, and the mechanism is still narrow: one `max_depth(1)` read, the same cap, the same visibility engine, no home-wide Listing and no skip-list. (2) "no home-expansion semantics the codebase does not have" is now only HALF true, deliberately: `skills::home_dir()` expands a leading `~/` in the completion QUERY, and NOTHING expands a tilde in a PATH that reaches the agent — which is exactly why an outside row INSERTS an absolute path while only the picker's DISPLAY is abbreviated. Teaching `FsBackend::resolve` to expand `~` was considered by ADR 0035 and refused for this ADR's own reason: a normalisation rule on the seam where the **Boundary** is decided. Everything else here stands, above all the decision in the title — `?` inserts a PATH and never injects content, whatever the path's shape, so the agent's policy-gated `read` stays the ONE enforcement point — so this is a widening of reach, not a `superseded-by`. One consequence belongs to the new reach and was not contemplated here: at the `Sandboxed` Beyond-boundary policy the picker now lists files the agent cannot read, and ADR 0035 refuses to filter rows by policy for this ADR's own reason — the picker is a view of the filesystem and not the enforcement point.

*Amended by the post-review pass (2026-10-10).* Two clauses above need correcting, and the second is this ADR's own safety property losing an absolute. **(1) The listing's rules.** The note about ADR 0034 says what the app keeps is "exactly the machine state no ignore file can ever speak for", and that is now TWO rules: the VCS metadata prune, and `name_is_completable` (`a540e23`), which refuses a NAME carrying `?` or a newline in both walks and refuses to descend into a DIRECTORY named that way. Say what it is rather than letting it look like a return of the skip-list: it is REPRESENTABILITY, a question about whether a name survives a round trip through the composer's grammar, so it consults no project convention and no name list, and `node_modules` stays the repo's decision exactly as 0034 left it. **(2) "Enter still sends."** The async clause above, and ADR 0034's narrowing of it, both rest on an empty `filtered` leaving the keyboard branches inert. That is still true of the **Listing**, and it is no longer true of **Directory completion**, deliberately: a directory selection leaves the picker with no rows and no note for the duration of one fetch, so nothing intercepted `Enter`, and the path the user had just asked for went to the model as raw text. `560f610` closes that window by holding `Enter` for exactly one round trip while an out-of-Space token's read is in flight, and it is bounded so this ADR's property survives where it matters: a REJECTED or EMPTY read counts as settled, so a directory that cannot be read never holds `Enter`, and a relative (Space) query is unaffected because its catalog resolves synchronously. The rule to carry forward is therefore "empty rows ⇒ no selectable rows, and `Enter` sends unless a fetch for a token that CANNOT be answered from what is on screen is still in flight": the exception exists for one round trip and for nothing longer.
