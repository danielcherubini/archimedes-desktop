# The session's context size is a SNAPSHOT — the last reported usage plus a local estimate of what came after

A **Native session**'s context size — the number the compaction threshold is compared against AND the number the composer's context bar renders — is **a snapshot: the most recent `Usage` the Provider reported (`input + output`), plus a local estimate of the transcript messages appended since that report. It is NEVER a sum of per-call usage.** The **Agent harness** keeps that one number in the `Compactor` (`context_tokens()`), and both consumers — `should_compact()` and the `context_usage_update` frame — read it from there. This replaces two divergent metrics: the trigger, which accumulated every call's usage, and the bar, which read the bare `input_tokens` of the last report.

**Why:** `Usage.input_tokens` is the FULL prompt — the entire prior context, re-sent on every iteration of the model loop. `Compactor::add_usage` did `+=`, so an agentic turn charged the same tokens once per model call and the tracked count grew roughly **quadratically** with turn length, while the threshold it is compared against (`context_window - reserve_tokens`) is a *context-size* budget. Compaction therefore tripped at about `window / N` model calls rather than when the context was full. Measured replay: a 200k window with the default 16,384 reserve (threshold 183,616) accumulated **188,058** from six prompts of 3,234 / 5,384 / 6,455 / 35,030 / 67,636 / 69,089 — while the real context was ~71,100 tokens. The user saw **"Compacting context…" at 35%**, which is the symptom that made this worth fixing properly rather than tuning: the harness was acting on a number the UI could not reproduce.

The bar's old metric was wrong in the other direction, which is why the two numbers disagreed. A bare `input_tokens` is the prompt as the Provider held it **before** the reply, so it under-counts the assistant message just produced and every tool result appended since — and on an endpoint that reports no usage at all it never moves. One metric, correct in the same way for both consumers, was the only stable answer: a UI that shows 35% while the trigger is over its threshold is not a cosmetic bug, it is an unexplainable agent.

**Considered Options**

- **Keep the accumulation, subtract an overlap estimate (rejected)** — there is no overlap to compute: each call's `input_tokens` is not an increment to reconcile but a *re-statement of the whole*, so summing them is a category error, not an imprecise estimate.
- **Use the bare `input_tokens` everywhere, including the trigger (rejected)** — consistent, but it under-measures the fresh tail (the reply + the tool batch), and on a usage-less endpoint it is pinned at 0, so compaction would never fire on exactly the endpoints the fallback exists for.
- **Use the local estimate everywhere and ignore `Usage` (rejected)** — what the harness did before `d122332` added `stream_options.include_usage` (no usage arrived, so the accumulation path never ran). It discards the one EXACT measurement available and leaves a 200k session permanently at the accuracy of `chars / 4`.
- **Two metrics, one per consumer (rejected)** — the pre-fix state. It is what made the incident incomprehensible in the UI; a threshold and a display that disagree about the same quantity cannot both be trusted.
- **Chosen: pi's `estimateContextTokens` snapshot** (`packages/agent/src/harness/compaction/compaction.ts` — `anchor + trailing`). The **anchor** is the last usage report (`input + output`, which already IS the transcript plus that reply's output); the **trailing** term is the local estimate of everything appended after it. A **watermark** (how many messages that report already accounts for) is what makes the two terms disjoint, so the model cannot double-count; and a session that never sees a usage report has a `0` anchor and a fully-trailing transcript — the same code path, no special case. Adopting pi's formulation here is a continuation, not a novelty: the harness already follows pi's compaction shape (the summary-as-`System`-message and prompt-state rules, ADR 0017).

**Consequences**

- **One number, two consumers.** `Compactor::context_tokens()` feeds `should_compact()` AND the `context_usage_update` frame that drives the composer's context bar. `AgentLoop::note_context()` is the single point where the context is recomputed after the transcript grows.
- **The frame also writes the `sessions` row** (`record_context_usage` — the store seam of ADR 0025), because the Client's store drops the entry when a Session closes and the row is the context bar's source for a closed session. That is why `note_context()` is called **once per logical context change, not per message**: a tool batch is one change, so a per-tool-call refresh would be N re-estimates and N DB writes for nothing new in between. And for the same reason a refresh that did NOT move the number emits NOTHING at all — the guard is equality on the value, not a delta threshold: when the stream reported `Usage` the `ProviderEvent::Usage` arm already anchored the count and emitted, and the assistant push that follows leaves the trailing slice EMPTY, so the refresh recomputes the identical value. A value-neutral refresh is therefore a value-identical IPC frame AND a value-identical `UPDATE` behind it (an `ensure_session_row` SELECT + write on the Supervisor's DB mutex), once per iteration, on the COMMON usage-reporting path. On a usage-less endpoint the value always moves (the reply / the tool batch grew the estimate), so the emissions that matter are untouched; the `Usage` arm's own emit stays unconditional, being the authoritative re-anchor that may legitimately move the number down.
- **The metric is re-anchored wherever the transcript grows** — the user prompt push, the assistant message push, and after the tool-result batch. The third is the one that mattered: `should_compact()` is read at the TOP of the iteration, so whatever was appended after the last re-anchor is invisible to the threshold, and tool results are the largest messages a turn produces (a `read`, a `grep`). Pre-fix a whole batch of huge output went uncounted — and on a usage-less endpoint, where the anchor is `0`, that estimate is the ONLY measurement there is, so one batch could blow past the window undetected and the Provider 400'd where compaction was due. The user prompt had the mirror-image lag: a large pasted prompt deferred a compaction that was already due by one model call — the call that had to send the oversized context.
- **A cancelled or failed turn retracts the snapshot** (`Compactor::turn_abandoned`, called from `settle_cancelled` / `settle_error` — i.e. from every turn exit — AND from the intra-turn mid-stream retry, guarded so it is a no-op when the reply did land). The **watermark** `record_usage` writes is `messages.len() + 1`: "the assistant reply lands at index `len`" — an assumption about the FUTURE stored in state read later, and a cancelled or failed turn deliberately NEVER makes that append (a partial assistant message is not persisted). Left alone, the next turn's user prompt lands at that index, INSIDE the watermark window, so `refresh` excludes it from the trailing term and a whole prompt goes unmeasured — the exact lag the tool-batch re-anchor above exists to prevent, resurrected — while the anchor still carries `output_tokens` for a reply the Provider never produced. So the watermark pulls back to what the transcript holds and the discarded reply's output leaves the anchor. This is the ADR's assumption made structurally repairable rather than left as a trap: the watermark is still an optimistic index, because being optimistic is what lets the trailing term be disjoint from the anchor, but every exit now reconciles it. The **mid-stream retry** is the case the exits structurally cannot reach: a stream that reports `Usage` and THEN fails retryably discards its partial reply (the retry re-generates it) and loops back to the TOP of the iteration — i.e. to `should_compact()` — without ever exiting the turn, so it re-reads a count still inflated by the discarded attempt's `output_tokens`, tokens the Provider generated for a reply nobody kept; a dying reply large enough to cross `window - reserve_tokens` therefore compacted the session before the retry's own call ran, which is premature compaction reborn in the one place the settle paths had no coverage. It now does the same reconcile the exits do. No frame is emitted at either reconcile — at an exit the next turn's prompt-time `note_context()` re-anchors and emits; for the retry loop-back no next turn is reached, so it is the retried call's own `ProviderEvent::Usage` arm (which emits unconditionally, being the authoritative re-anchor) or, if that call reports no usage, the surviving reply's `note_context()` push that re-emits (the value at a reconcile sits strictly between two authoritative readings, and the frame also writes the `sessions` row).
- **Three paths may move the number down, and only those three**: `reestimate` (the RESET — resume, post-compaction, `prepend_system`, and `set_model`'s window switch: a compacted, rehydrated, or re-windowed transcript is a genuinely new baseline, and the estimate REPLACES the count and clears the anchor); `turn_abandoned` (a cancelled or failed turn — and a retried model call within a turn — retracts the reply the watermark optimistically assumed); and `record_usage` itself — the authoritative re-anchor REPLACES the snapshot with the Provider's own number, which may correct an inflated trailing estimate downward. All three are legitimate new baselines or corrections — `reestimate` moving DOWN is a feature, not a violation of the invariant below, and none of the three is a usage-less call, so the invariant stands.
- **The invariant the model buys**: the anchor moves only when the Provider actually reports, and the trailing term is purely additive, so **a usage-less call can never shrink the metric.** That is structural, so the previous `raise_context_from_estimate` floor-raiser — which existed to special-case exactly that failure — was deleted rather than kept as a belt-and-braces guard. A guard for an impossibility is a future reader's puzzle.
- **`Usage` carries only `input_tokens` / `output_tokens`, so the anchor is conservative in the WRONG direction on a cache-heavy wire.** pi adds `cacheRead + cacheWrite` to its anchor; the Anthropic Messages parser reads `usage.input_tokens` and drops the cache fields, and a cached prefix is precisely the part of the prompt that `input_tokens` does not count — so an Anthropic session's snapshot under-reads its real context, and compaction arrives **late** (a Provider 400) rather than early. Deliberately out of scope for this fix: the seam to widen is the `Usage` struct in `provider/types.rs` plus the three wire parsers, and the anchor formula is the only consumer. Recorded here so that whoever widens it knows the snapshot is already correct once those fields arrive.
- **Between two usage reports the number is approximate** — the trailing estimate is `chars / 4`, plus a flat cost per tool call and +1000 per image block. Accepted: the next usage report re-anchors exactly, so the error is bounded by one turn's tail rather than compounding, and the alternative (no anchor at all) is strictly worse.
- **`set_model` rebuilds the `Compactor` and so drops the anchor** (the context window — and therefore the threshold — is per-model), so it **re-estimates immediately** on the unchanged transcript and sets the frame's value from that re-estimate rather than emitting the previous number. Emitting the old value would breach this ADR's own one-number, two-consumers rule for as long as it takes the next prompt to arrive: the bar would read the old count while `should_compact()` read the freshly-reset `0`, and switching INTO a smaller window would defer a compaction that is already due by a whole model call (the call that has to send the oversized context). Re-estimating at the moment of the switch makes the frame, the tracked count, and the new threshold agree the instant the window changes; the number usually lands where it was (the transcript did not change), and the next report the Provider sends re-anchors it exactly, as ever.
- **The vocabulary of the model is now load-bearing** in the harness's comments, and any future reader of `compact.rs` should have it: the **anchor** (the last usage the Provider reported), the **trailing** term (the local estimate after it), the **watermark** (how many messages the report already covers), and to **re-anchor** (recompute the snapshot after the transcript grows).
