# Native Agent Harness Plan

**Goal:** Make the desktop the Agent harness — move the built-in tools into the desktop (Phase 1) and add an in-process native agent loop that runs a full conversation with no pi dependency (Phase 2).

**Architecture:** The Rust backend gains a `harness` module (an in-process `AgentLoop` tokio task per native session + an OpenAI-compatible `Provider` + a `ToolRegistry` of Rust executors + a SQLite `SessionStore` + `Compactor`/`RetryPolicy`). The `SessionDriver` generalizes to drive two session kinds (external = existing `PiRpc` backend; native = the in-process `AgentLoop`), both emitting the same normalized event shapes. The `tools.ts` override extension (Phase 1) re-registers the built-ins as bridge delegates; the Rust executors built in Phase 1 are reused in-process by the native harness in Phase 2.

**Tech Stack:** Rust (Tauri 2 backend, tokio, reqwest, serde, rusqlite), TypeScript (the embedded `tools.ts` extension), React 19/TS (frontend — unchanged event contract).

**Conventions (from AGENTS.md):** TDD (failing test first), `cargo test` / `cargo clippy --all-targets` (0 warnings) / `cargo fmt --check` from `src-tauri/`; `pnpm test` / `pnpm build` from the repo root. The desktop is the **Client**; pi is the **Agent** (external). A **Native session** is a Session whose harness is the desktop's in-process runtime; an **External session** is one whose harness is a spawned agent process. See `CONTEXT.md` + ADR 0009/0010/0011/0012.

### Task 1: Rust tool executors (the `*Operations` seams ported to Rust)

**Context:**
Phase 1 moves the built-in tools into the desktop so the desktop owns tool *execution* (pi's built-ins are disabled via `--no-builtin-tools`). This task builds the Rust executors — one per built-in tool — that both the Phase 1 bridge round-trip (external sessions) and the Phase 2 native harness (in-process) will call. Each executor takes the tool's params, executes **sandboxed to the session's `cwd`** (reusing the existing `FsBackend` from `src-tauri/src/agent/fs_backend.rs`), and returns a **pi-shaped** result `{ content: Vec<ContentBlock>, details: Option<serde_json::Value>, is_error: bool }` so the LLM sees `content` and the UI sees `details` (matching pi's built-in renderers). The executors are pure functions (no I/O side effects beyond the tool's own action) so they are trivially unit-testable. `powershell` is **excluded** here (Windows-only; the bridge is Linux-only) — it is added in Task 6.

**What to implement:**
- A `ToolResult` struct: `{ content: Vec<ContentBlock>, details: Option<serde_json::Value>, is_error: bool }` where `ContentBlock` is `{ text: Option<String>, image: Option<ImageRef> }` (a serde enum, `tag = "type"`, variants `text` / `image`). The Rust field stays `is_error` (idiomatic); only the **serialized** name is `isError` — pi's tool-result wire contract + every existing bridge handler use `isError` (`bridge.rs:1418,1486,1621,1686,1761,1812-1842`; the frozen `session.rs:2841` shape; a snake_case `is_error` would make pi render every failure as a success). This mirrors pi's `AgentToolResult` shape (research F5: `content: (Text|Image)[]`, `details`, `isError`).
- A `ToolCtx` struct: `{ cwd: PathBuf, cancel: CancellationToken }` (the `cwd` is the sandbox root; `cancel` is a `tokio_util::sync::CancellationToken` wired to the tool's AbortSignal). Use the existing `FsBackend { root }` for path validation — **via the new `pub fn validate` / `pub fn read_bytes` seam** (the existing `read`/`write` are `read_to_string`-only and `resolve`/`check_under_root` are private, so `ls`/`find`/`grep`/binary-image `read` have no seam today; Task 1 adds them additively, no behavior change).
- One async executor per tool, each `async fn exec_<tool>(ctx: &ToolCtx, params: &serde_json::Value) -> ToolResult`:
  - `exec_bash(ctx, params)`: `params = { command: String, timeout_ms?: u64 }`. Run via `tokio::process::Command` with a shell (`sh -c` on Unix; the command is NOT re-parsed — pass verbatim) with `current_dir = ctx.cwd`. Capture stdout+stderr (interleaved, capped at a max, e.g. 100 KB → `truncated: true` on overflow). On `ctx.cancel` being triggered or `timeout_ms` elapsing, **kill the child** (`.kill()`). Return `content = [text: <output>]`, `details = { exitCode: i32, truncated: bool, cancelled: bool }` (**camelCase `exitCode`** — matches the acceptance criterion + the established wire convention, `handle_sudo_exec`'s `details.exitCode`, `bridge.rs:1810-1842`), `is_error = (exit_code != 0 || cancelled)`. **Security note (reviewer-corrected):** `bash` is **gated, not sandboxed** — `sh -c` can read/write anywhere (a `cat /etc/passwd` is not blocked by `cwd`); the permission gate (Task 3 / the existing `gate.ts`) is the control, exactly as in pi's own `bash`. Only the **path-param** tools (`read`/`write`/`edit`/`find`/`grep`/`ls`) are sandbox-validated via `FsBackend`.
  - `exec_read(ctx, params)`: `params = { path: String, offset?: u64, limit?: u64 }`. Validate `path` against `ctx.cwd` (canonicalize; reject escapes via `FsBackend`). Read the file (text) or return an image `ContentBlock` (if the extension is an image type). `offset`/`limit` are 1-indexed line range (default: whole file, capped at a max line count, e.g. 2000). Return `content = [text | image]`, `details = { path, lines: usize }`, `is_error = (I/O error)`.
  - `exec_write(ctx, params)`: `params = { path: String, content: String }`. Validate `path` against `ctx.cwd`. Create parent dirs. Write the file (overwrite). Return `content = [text: "Wrote <n> bytes to <path>"]`, `details = { path, bytes: usize }`, `is_error = (I/O error)`.
  - `exec_edit(ctx, params)`: `params = { path: String, old_text: String, new_text: String, replace_all?: bool }`. Validate `path` against `ctx.cwd`. Read the file. If `old_text` not found → `is_error = true`, `content = [text: "old_text not found in <path>"]`. Else replace the first occurrence (or all if `replace_all`), write back. Return `content = [text: "Edited <path>"]`, `details = { path, occurrences: usize, diff: String }` (the `diff` is a unified diff of the change), `is_error = (not found | I/O error)`.
  - `exec_find(ctx, params)`: `params = { pattern: String, path?: String, max_results?: u32 }`. Validate `path` (default `ctx.cwd`) against `ctx.cwd`. Shell out to `fd` (`fd -g <pattern> <path> --max-results <n>`) if available, else fall back to a `walkdir` glob. Return `content = [text: <newline-joined matching paths>]`, `details = { matches: usize, truncated: bool }`, `is_error = (no fd + walkdir error)`.
  - `exec_grep(ctx, params)`: `params = { pattern: String, path?: String, glob?: String, max_results?: u32, -i?: bool }`. Validate `path` (default `ctx.cwd`) against `ctx.cwd`. Shell out to `ripgrep` (`rg <flags> <pattern> <path>`) with the flags mapped from params (`-i`, `--glob`, `-m <n>`). Return `content = [text: <ripgrep output>]`, `details = { matches: usize, truncated: bool }`, `is_error = (ripgrep missing + no fallback)`.
  - `exec_ls(ctx, params)`: `params = { path?: String, long?: bool }`. Validate `path` (default `ctx.cwd`) against `ctx.cwd`. List the directory (`read_dir`). Return `content = [text: <newline-joined entries>]`, `details = { entries: usize }`, `is_error = (I/O error)`.
- A dispatch function: `pub async fn execute_tool(ctx: &ToolCtx, tool: &str, params: &serde_json::Value) -> ToolResult` — a `match` on `tool` (`"bash" | "read" | "write" | "edit" | "find" | "grep" | "ls"`) calling the right executor; unknown tool → `is_error = true`, `content = [text: "unknown tool: <tool>"]`.
- **What NOT to change:** `fs_backend.rs` gets **additive visibility/API only** (no behavior change to the existing `read`/`write`); do NOT add a `powershell` executor (Windows-only; added when Windows native sessions are in scope — **out of scope here**); do NOT wire these into the bridge yet (Task 2); do NOT add the `--no-builtin-tools` spawn yet (Task 3); do NOT touch `agent/mod.rs` (its `pub mod tools;` is already correct).
