# Pi RPC Phase 2 — the Suite's Tools Live in the Desktop Plan

**Goal:** Move the pi-archimedes suite tools the desktop must own (`ask` / `sudo_exec` / `manage_todo_list`) out of the agent process and into the desktop — the agent's copies become thin delegates (`execute()` = a bridge round-trip), and the desktop owns the execution + result shaping. `subagent` is excluded (already desktop-executed). Pi's built-in tools are OUT of scope (they keep running in the agent; that is Phase 3, the Gondolin `--no-builtin-tools` pattern).

**Architecture:** A new desktop-provided extension (`tools.ts`, embedded via `include_str!` exactly like `gate.ts`) re-registers `ask` / `sudo_exec` / `manage_todo_list` with the SAME name + schema as the suite's versions but `execute()` = "send the params to the desktop over the bridge, await the result, return it (shaped, for `ask`)". The extension registers the tools **inside `pi.on("session_start", …)` — NOT at load time** (see the critical mechanism note below). The extension is SELF-GATED on the bridge env (its first lines), so it is inert on a bridge-less spawn (macOS) — the suite's original agent-local tools then remain (no regression). The desktop gains two new method-aware bridge handlers (`sudo_exec`, `todo_update`) + a shared `TodoStore`; `dispatch_subagent` is already method-aware and `ask` already flows through the generic `bridge-request` path (both already desktop-side).

**Tech Stack:** Rust (Tauri 2, tokio, serde) for the desktop-side execution; TypeScript (a single self-contained extension file, node:net) for the agent-side override. **No frontend changes** — the existing `TodoBoardPanel`/`useBridge` (todo) and `SudoConfirmModal`/`SudoPasswordModal`/`respondBridgeRequest` (sudo) are reused. Bridge wire: one JSONL frame per connection, `{v:1, type:"request", id, method, source, params}` → `{v:1, type:"response", id, result}` / `{…error}`.

**Background reading (required before executing any task):** `docs/decisions/0009-rpc-replaces-acp.md` (the 3-phase plan — this is Phase 2), `docs/research/pi-rpc-replaces-acp.md` §F1 + the tool-delegation verdict (the `registerTool` same-name override is THE mechanism; the `tool_call` hook is gate-only and CANNOT supply a result; `extension_ui`/`ctx.ui` is a UI-dialog protocol and CANNOT express a tool round-trip with a structured result — so the bridge is the channel; the bridge is fail-closed on macOS → Phase 2 is macOS-excluded). The suite source of truth: `/home/daniel/Coding/Javascript/pi-archimedes/packages/{ask,sudo,todo}/src/*.ts` (the tools' current `execute()` + result shapes). The installed suite is a single extension entry (`~/.pi/agent/extensions/pi-archimedes/package.json` → `"pi": {"extensions": ["meta/src/index.ts"]}`).

**CRITICAL MECHANISM NOTE (verified empirically against pi 0.87.1 — read before executing Task 2):**

1. **Two extensions registering the SAME tool name at LOAD time → `process.exit(1)`.** `DefaultResourceLoader.addExtensionConflictDiagnostics` (`dist/core/resource-loader.js:459-465, 843-871`) flags same-name tools from different extension paths at load-finalization and `main.js` maps them to `type:"error"` diagnostics → `process.exit(1)`. Verified: `pi --mode rpc -e a.ts -e b.ts` (both `registerTool("foo_tool")` at factory time) → `Error: Failed to load extension "…/b.ts": Tool "foo_tool" conflicts with …/a.ts`, `exit=1`. The suite registers `ask`/`sudo_exec`/`manage_todo_list` at **load time** (the `meta/src/index.ts` factory calls `registerAsk`/`registerSudo`/`registerTodo`, each of which calls `pi.registerTool` immediately — `packages/ask/src/index.ts:27`, `packages/sudo/src/index.ts:19`, `packages/todo/src/index.ts:84`) and `subagent` at **session_start** (lazy-loaded, `meta/src/index.ts:127-128,162`). So a `tools.ts` that `registerTool`s at load time would brick every bridge-enabled spawn.
2. **The fix: register inside `pi.on("session_start", …)` (deferred).** `registerTool` (`dist/core/extensions/loader.js:222-230`) adds the tool to `extension.tools` AND **auto-calls `runtime.refreshTools()`** — so a deferred registration is picked up with no manual refresh. Conflict detection runs once at load-finalization over `ext.tools`; a deferred (session_start) registration is absent at load time → no conflict. Verified: `pi --mode rpc -e a_deferred.ts -e b_loadtime.ts` (a registers `foo_tool` at `session_start`, b at load time) → **no exit**, and the system prompt's tools section shows `a`'s `promptSnippet` — the deferred registration won.
3. **The override wins because CLI `-e` extensions load FIRST and the merge is FIRST-WINS.** `dist/core/resource-loader.js:402-420` (`loadCurrentExtensionSet`): `extensionPaths = mergePaths(cliEnabledExtensions, enabledExtensions)`; `mergePaths` (`:656-667`) = `[...primary, ...additional]` (CLI first). `getAllRegisteredTools` (`dist/core/extensions/runner.js:369-381`) iterates `this.extensions` in order and keeps the **first** registration per name. So `tools.ts` (a CLI `-e` extension, first) beats the suite (a global/discovered extension, later) for every same-name tool, regardless of registration timing.
4. **Consequence for `tools.ts`:** (a) register the three tools inside a `session_start` handler, (b) the handler is only registered when the self-gate passes (bridge env present), (c) no manual `refreshTools()` needed (auto, loader.js:229), (d) `tools.ts` is first → its definitions win. Any FUTURE same-name `registerTool` at load time is a startup brick — keep all `tools.ts` registration deferred.

**Scope decision (locked):** `ask` / `sudo_exec` / `manage_todo_list` are overridden (desktop-owned). `subagent` is NOT overridden — it is already desktop-executed (the suite's `subagent` tool delegates to the desktop's `dispatch_subagent`, which spawns the child session on the desktop; the suite's tool is already a delegate). Overriding `subagent` would require replicating the suite's agent-discovery / resolution / fan-out (`packages/subagent/src/{execute,agent-manager,model-validation,frontmatter-io}.ts`) because the desktop's `dispatch_params` (`bridge.rs:655-696`) expects the suite's RESOLVED launch shape `{agentName, task, systemPrompt, model, thinking, tools}` (built by `packages/subagent/src/dispatch.ts:83-92` after `discoverAgents` + agent-file resolution + `resolveModel`), NOT the raw tool params `{agent?, task?, tasks?, model?, cwd?, async?}` — a thin pass-through would silently drop named agents, always fail parallel `tasks` (no `task` → `invalid params`), and lose `async` semantics. `list_agents` (also suite-registered, `packages/subagent/src/index.ts:260`) is likewise NOT overridden. Pi's built-in tools (`bash`/`edit`/`write`/`read`/`find`/`grep`) are NOT re-registered, NOT disabled, NOT touched (Phase 3).

**Locked design decisions (do not re-litigate):**
- The round-trip channel is the **bridge** (the existing peer-verified Unix socket), NOT `extension_ui`/`ctx.ui` (a UI-dialog protocol that cannot carry a structured tool result). The override carries a minimal self-contained bridge client (node:net, one fresh connection per request — the bridge is one-connection-per-message).
- The override extension is a **separate file** (`tools.ts`) from `gate.ts` (different concerns). The desktop injects BOTH via `-e <gate> -e <tools>`.
- The override SELF-GATES on the bridge env. Use **all four** env vars the suite's gate checks (`PI_ARCHIMEDES_BRIDGE === "1" && PI_ARCHIMEDES_BRIDGE_SOCKET && PI_ARCHIMEDES_BRIDGE_SESSION && PI_ARCHIMEDES_BRIDGE_SERVER_PID`, `packages/core/src/bridge/index.ts:137-140`) — equivalent for desktop spawns (the desktop sets all four, `session.rs:2428-2438`) and drift-safe.
- **No frontend changes.** The todo board reuses the existing `todos_update` push → `useBridge.applyTodoUpdate` → `TodoBoardPanel` (`src/store/bridge.ts:49-138`, `src/components/TodoBoardPanel.tsx`, hosted in `src/components/SidePane.tsx`). The sudo flow reuses the existing `bridge-request` `method:"confirm"`/`"password"` → `SudoConfirmModal`/`SudoPasswordModal` → `respondBridgeRequest` (`src/components/SudoConfirmModal.tsx`, `SudoPasswordModal.tsx`, hosted in `src/components/ChatStream.tsx:977/984` + `SubagentPanel.tsx:239/246`).
- `ask` result-shaping lives in the **override** (it maps the desktop's raw `AskResponsePayload` `{cancelled, results}` → the suite's `AgentToolResult` shape, porting `packages/ask/src/tool.ts:174-186,265-271` `responseToResults` + `buildAskSessionContent`). `sudo_exec` + `todo_update` result-shaping lives in the **desktop** (the handlers return `{content, details}`; the override passes through).
- `gate.ts`'s `GATED` set drops `sudo_exec` (the desktop's `sudo_exec` handler is the single confirm — avoids a double confirm: the gate's `tool_call` hook fires regardless of which definition implements the tool, so without the drop the user sees the generic permission prompt AND the sudo command confirm). `bash`/`edit`/`write` stay gated (built-in, NOT overridden).

     import { connect, type Socket } from "node:net";
     import { randomUUID } from "node:crypto";
     function bridgeRequest<T = any>(
       method: string,
       params: any,
       signal: AbortSignal | undefined,
       timeoutMs: number | null, // null = no timeout (matches the suite's channel.ts: undefined=5min, null=none)
     ): Promise<T> {
       const socketPath = process.env.PI_ARCHIMEDES_BRIDGE_SOCKET!;
       return new Promise<T>((resolve, reject) => {
         let settled = false;
         let conn: Socket | undefined; // declared BEFORE fail (a pre-aborted signal calls fail() before connect() — conn?.destroy() must not throw a ReferenceError; the suite handles pre-aborted signals, core/bridge/index.ts:101-104)
         let timer: NodeJS.Timeout | undefined;
         let onAbort: (() => void) | undefined;
         // All terminal paths funnel through here: idempotent behind the `settled` guard, and it CLEANS UP the timer + the abort listener (so a pre-aborted-signal reject or a timeout does not pin the event loop or leak a stale `abort` listener on the turn's long-lived AbortSignal — the suite removes its listener on settle, core/bridge/index.ts:102-107). `timer`/`onAbort` are declared (not yet assigned) above so the references are safe: `fail` is only ever called after both are assigned.
         const fail = (e: Error) => { if (!settled) { settled = true; if (timer) clearTimeout(timer); if (onAbort && signal) signal.removeEventListener("abort", onAbort); conn?.destroy(); reject(e); } };
         // Arm the timer ONLY when timeoutMs > 0 (a 0/negative/absent value = no timer).
         if (timeoutMs !== null && timeoutMs > 0) {
           timer = setTimeout(() => fail(new Error("timeout")), timeoutMs);
         }
         onAbort = () => fail(new Error("cancelled")); // wire the tool's AbortSignal → destroy the socket (the desktop sees EOF → aborts in-flight execution)
         if (signal) { if (signal.aborted) { onAbort!(); return; } signal.addEventListener("abort", onAbort!, { once: true }); }
         conn = connect(socketPath);
         let buf = "";
         conn.on("data", (c: Buffer) => {
           buf += c.toString();
           const nl = buf.indexOf("\n");
           if (nl === -1) return;
           if (timer) clearTimeout(timer);
           if (signal) signal.removeEventListener("abort", onAbort);
           const line = buf.slice(0, nl);
           conn.destroy();
           let frame: any;
           try { frame = JSON.parse(line); } catch (e: any) { return fail(new Error(`bad bridge frame: ${e.message}`)); } // try/catch — an uncaught throw in a socket handler crashes the agent
           if (frame.type !== "response") return fail(new Error("unexpected bridge frame"));
           if (frame.error !== undefined) { return fail(Object.assign(new Error(frame.error), { isError: true, raw: frame })); } // error frame → a typed error via `fail` (which cleans up the timer + abort listener); the override maps it to an isError result
           settled = true; resolve(frame.result); // success path: `fail`-style cleanup already done above (timer + listener cleared before this line)
         });
         conn.on("error", (e) => fail(e));
         conn.on("close", () => fail(new Error("bridge connection closed"))); // a clean close with NO `error` event is terminal (the suite's channel.ts:19-21,189 — peer-verification rejection, an unparseable/oversized frame, or a desktop crash). REQUIRED for `sudo_exec` (`timeoutMs: null` = no timer): without it the promise never settles and the whole agent turn hangs until a manual abort.
         conn.on("connect", () => {
           conn.write(JSON.stringify({ v: 1, type: "request", id: randomUUID(), method, source: "main", params }) + "\n");
         });
       });
     }
