# Two-Session Hang Investigation Plan

**Goal:** Root-cause (or demonstrate the resolution of) the 2026-09-15 hang — two concurrent ACP sessions on one tokio runtime hanging `send_prompt` 60+ seconds — and decide the one-live cap's fate.

**Architecture:** A diagnostic repro harness (two REAL pi ACP sessions, one runtime, hard timeout) gates the whole investigation: if it passes, the hang is gone and the cap lifts; if it hangs, a version-matrix bisect + mechanism-isolation experiments pin the layer (SDK / async-io / tokio scheduler / our code), then a fix (ours or upstream) + a regression test, then the cap decision.

**Tech Stack:** Rust (Tauri 2, tokio, `agent-client-protocol` 2.x), the real `pi-acp` adapter (resolved from PATH / a `PI_ACP_BINARY` env override — with `pi` on PATH as its GRANDCHILD: pi-acp spawns `pi --mode rpc --no-themes`), ADRs 0002/0004.

**Repos, paths and commands used in every task below:**
- Desktop repo root: `/home/daniel/Coding/AI/archimedes-desktop` (Rust under `src-tauri/`).
- Rust: `cd src-tauri && cargo test --test <name>`, `cargo clippy --all-targets` (0 warnings), `cargo fmt --check`.
- ADRs: `docs/decisions/0002-one-live-acp-session.md` (the cap + the 2026-09-15 incident: "reproduced (real-app topology, live) that two concurrent ACP sessions on one tokio runtime hang `send_prompt` for 60+ seconds, with the suspected cause at the SDK/async-io level (two long-lived per-connection transport tasks sharing one global async-io reactor). Root cause was never confirmed and the diagnostic repro was **deleted**."), `docs/decisions/0004-subagent-worker-runtime.md` (the workaround: subagents on a dedicated worker runtime; option 3 = root-cause + fix + lift the cap; "lifting the cap is a one-token policy flip once it's fixed").

**The one-live policy (what "lifting the cap" means):** `SessionManager::supersede_live_sessions` (`src-tauri/src/acp/session.rs:752`) initiates a `replaced` close of every other live session; it is called from `start_session` (session.rs:816) and `resume_session` (session.rs:924). Lifting the cap = remove those two call sites (+ the `replaced`-reason behavior they produce) and update the policy tests. The schema is multi-session-safe (ADR 0002: "if the SDK hang is later fixed, lifting the cap is a one-token policy flip").

**Investigation rules (for the executing agent):**
- This is an INVESTIGATION, not a feature: tasks 2-3 are CONDITIONAL on the task-1 repro hanging. If the repro passes, jump straight to task 4 with the "resolved" conclusion — do NOT invent work.
- Every experiment gets a hard timeout (10 s, `tokio::time::timeout`) so a hang is a CLEAN RED test, never a stalled CI run (the `subagent_concurrency.rs` pattern — read it first).
- Record every experiment's outcome in the task's commit message (a one-line "EXPERIMENT LOG" section): version, topology, hang or not, wall time. The log IS the deliverable's evidence.
- Do NOT change production code in tasks 1-2 (diagnostic tests only). Production changes happen only in task 3 (a fix) or task 4 (the cap decision).

(The worse variant: if the harness instead awaits `connect_with` inline, `spawn_real_session` never returns → a false hang repro. The block-until-close + channels pattern avoids both.)
